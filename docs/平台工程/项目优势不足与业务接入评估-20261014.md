# 项目优势、不足与业务接入评估

- 评估日期：2026-10-14。
- 源码基线：`619d993`（评估时的 `main`）。
- 范围：25 个 Maven 模块的职责与配置、重点业务源码、数据库迁移、Vue 控制台及已有验证记录；并非所有代码逐行安全审计。
- 本轮实际验证：直接编译当前 `SqlGuard` 并执行 6 个隔离用例，没有连接业务数据库；未重跑全量测试、生产压测或真实第三方业务验收。

## 1. 总体判断

项目的工程底座较强，知识库治理最完整，但业务接入深度和产品化程度落后于技术能力。当前适合发展为“企业知识服务＋受控业务办理”的 AI 平台。

| 维度 | 判断 | 依据与限制 |
| --- | --- | --- |
| AI 能力覆盖 | 较强 | 对话、RAG、Agent、问数、多模态和互操作已有实现；默认启用、凭据与真实业务验收需分别确认 |
| 知识治理 | 较强 | 版本化入库、审核发布、同步恢复、检索质量回归已有实现 |
| 任务可靠性 | 较强 | 持久化状态、租约代次、事件回放、Inbox/Outbox、幂等回执 |
| 业务闭环 | 部分具备 | 订单偏查询，退款偏审批与答复，税票偏批次一致性检查 |
| 外部系统接入 | 部分具备 | 已有协议与渠道适配，但真实数据源、账号映射和业务结果回写仍有缺口 |
| 生产就绪证据 | 不完整 | SQL 护栏缺陷已复现，依赖扫描有失败记录，真实业务负载与完整第三方联调未在本轮验证 |

以上为源码与证据驱动的定性判断，不是性能评分、市场竞争排名或生产认证。

## 4. SQL 护栏隔离验证

### 4.1 结果与边界

直接编译基线的 `SqlGuard.java`，使用虚构租户 `tenantA`、白名单 `orders/customers`、`maxRows=100`、`enforceTenantPredicate=true`。没有建立数据库连接，没有访问或修改业务数据。

| 用例 | 安全预期 | 实际结果 |
| --- | --- | --- |
| 正常租户查询 | 放行并追加 LIMIT 100 | 符合预期 |
| 完全缺少租户条件 | 拒绝 | 符合预期 |
| OR 条件使租户过滤失效 | 拒绝 | 错误放行 |
| 关联查询只约束第一张表的租户 | 拒绝 | 错误放行 |
| 逗号连接引入白名单外表 | 拒绝 | 错误放行 |
| 显式 LIMIT 1000000 | 拒绝或收紧到 100 | 放行且不收紧 |

验证只证明校验器的返回行为。实际影响还取决于数据库权限、数据分布、上游可达路径等，不能将结果写成“已从线上读取其他租户数据”。只读数据库权限约束写操作，不能自动解决行级读取授权。

### 4.2 可复现命令

在仓库根目录执行，要求 Python 3 与 JDK 21。临时源码与 class 文件均位于系统临时目录，退出后清理；不修改仓库或连接外部组件。

```bash
python3 - <<'PY'
from pathlib import Path
import subprocess
import tempfile

source = Path('analytics-service/src/main/java/com/lrj/platform/analytics/SqlGuard.java').resolve()
probe = '''import com.lrj.platform.analytics.SqlGuard;
import java.util.List;
public class SqlGuardProbe {
 public static void main(String[] args) {
  var guard = new SqlGuard(List.of("orders", "customers"), List.of("orders", "customers"), 100, true);
  String[][] cases = {
   {"valid_tenant", "SELECT id FROM orders WHERE tenant_id='tenantA'"},
   {"missing_tenant", "SELECT id FROM orders"},
   {"or_bypasses_tenant", "SELECT id FROM orders WHERE tenant_id='tenantA' OR 1=1"},
   {"join_missing_second_tenant", "SELECT c.name FROM orders o JOIN customers c ON 1=1 WHERE o.tenant_id='tenantA'"},
   {"comma_table_allowlist_bypass", "SELECT s.* FROM orders o, secrets s WHERE o.tenant_id='tenantA'"},
   {"oversized_limit", "SELECT id FROM orders WHERE tenant_id='tenantA' LIMIT 1000000"}
  };
  for (var c : cases) {
   var r = guard.check(c[1], "tenantA");
   System.out.println(c[0]+": allowed="+r.allowed()+", reason="+r.reason()+", capped="+(r.sql()!=null && r.sql().endsWith("LIMIT 100")));
  }
 }
}'''
with tempfile.TemporaryDirectory(prefix='platform-review-sql-') as out:
    file = Path(out, 'SqlGuardProbe.java')
    file.write_text(probe)
    subprocess.run(['javac', '-d', out, str(source), str(file)], check=True)
    subprocess.run(['java', '-cp', out, 'SqlGuardProbe'], check=True)
PY
```

基线输出：

```text
valid_tenant: allowed=true, reason=null, capped=true
missing_tenant: allowed=false, reason=missing tenant filter (require tenant_id='tenanta'), capped=false
or_bypasses_tenant: allowed=true, reason=null, capped=true
join_missing_second_tenant: allowed=true, reason=null, capped=true
comma_table_allowlist_bypass: allowed=true, reason=null, capped=true
oversized_limit: allowed=true, reason=null, capped=false
```

这里的 `capped` 仅检查该组样例是否以 `LIMIT 100` 结尾，不是通用 SQL 安全判定器。命令成功退出也不代表护栏安全，必须对照每条用例的安全预期。

## 5. 现有业务接入缺口

| 业务 | 已有能力 | 接入不足 | 下一步闭环 |
| --- | --- | --- | --- |
| 企业知识库 | 文件入库、HTTP 增量同步、审核发布、质量回归 | 最近本地部署记录的来源为空；通用 Feed 不承载原系统逐文档 ACL | 真实来源→身份/权限映射→增量更新与撤权→检索验证 |

| 订单查询 | 本地关系库的租户隔离只读查询 | 尚缺真实 OMS/ERP、物流、售后历史及终端客户归属校验 | 客户识别→订单/物流→售后记录 |
| 退款审批 | 发起、认领、人工审批、答复与可靠通知 | 流程结束在生成答复，尚未见支付退款与结果核对链路 | 审批→外部退款→状态确认→失败处理/对账 |
| 发票审查 | 批次内重复、金额勾稽、税额计算、期间检查与 AI 解释 | 请求不持久化；缺跨批次查重、审核案件、人工复核与报销单关联 | 票据→审核记录→报销单→人工复核→归档 |
| 经营问数 | 自然语言 SQL、只读查询与解释 | 护栏缺陷；业务指标口径、字段权限和真实问题集需补齐 | 批准指标→受控查询→口径解释→业务验收 |

## 7. 建设顺序与触发条件

| 阶段 | 分类 | 工作 | 完成依据 |
| --- | --- | --- | --- |
| A | MUST_FIX | 修复 SQL 护栏；明确业务对象权限、敏感知识授权；整改依赖扫描；按实际多租户场景核验预算 | 反例回归、授权失败路径、适用供应链检查及部署配置证据 |
| B | NATURAL_EVOLUTION | 一个真实业务纵向闭环：数据源、身份、查询、人工处理、结果通知、反馈 | 使用真实授权系统与业务样本验收，区分提交成功和业务完成 |
| C | PLATFORMIZATION | 在第二/第三条业务线重复出现认证、对象映射、同步恢复与审批模板需求时沉淀公共能力 | 至少两个实际消费者、统一契约、故障恢复和接入成本对比 |
| D | EXPLORATION | 根据客户需求选择销售支持、采购材料等新场景 | 有明确使用者、输入来源、业务负责人和可观察收益 |

依赖关系：A 的适用前置条件 → B 的真实场景 → C 的重复需求抽象；D 按业务价值与前置条件独立评估。未启动场景不因本报告变成实施任务。

现阶段不建议继续堆叠通用 Agent 模式、增加服务拆分、再造任务/工作流引擎，或同时铺开多个行业。只有实际容量、团队所有权或业务差异证实需要时才重评这些方向。
