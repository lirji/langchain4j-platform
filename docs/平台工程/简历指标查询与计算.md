# 简历指标查询与计算

本文说明如何为本项目取得可复现、可解释的工程指标，包括：

- RAG Recall@K
- NL2SQL 执行成功率与结果正确率
- 接口 P95 响应时间
- L1 语义缓存命中率
- 已注册租户数与经过验证的租户容量

> 简历只应填写实际测得的数据。每个数字至少保留测试集版本、环境、配置、时间窗口和原始报告；不要把配置值、演示数据量或理论能力写成实测结果。

## 1. 指标口径总览

| 指标 | 推荐简历口径 | 当前是否可直接查询 |
| --- | --- | --- |
| RAG 召回率 | 固定黄金集上的 `Recall@5`，同时给出用例数 | 可以，使用 `POST /eval/retrieval` |
| NL2SQL 成功率 | 固定黄金集上的结果正确率；执行成功率作为辅助指标 | 需建立黄金集；当前 smoke 不能证明正确率 |
| P95 响应时间 | 指定接口、并发/QPS、数据规模和缓存状态下的 P95 | 需使用 k6 等压测；当前 Prometheus 配置不完整 |
| 缓存命中率 | L1 语义缓存 `hit / (hit + miss)` | 当前没有 hit/miss 计数器，需补埋点或做受控测试 |
| 支持租户数量 | 在给定负载下通过容量和隔离测试的租户数 | 不能从配置推导；只能直接查询已注册/活跃租户数 |

## 2. RAG Recall@K

### 2.1 计算方式

对第 `i` 个问题，设人工标注的相关文档集合为 `G_i`，Top-K 检索结果为 `R_i@K`：

```text
Recall_i@K = |G_i ∩ R_i@K| / |G_i|

平均 Recall@K = (Σ Recall_i@K) / N
```

项目的 `eval-service` 使用宏平均，即先计算每个问题的 Recall@K，再对所有问题取平均。文件级标注（例如 `project-faq.md`）可以命中该文件的任意 chunk；带 `#` 的标注（例如 `project-faq.md#2`）只匹配指定 chunk。

### 2.2 准备黄金集

建议准备至少 30～50 条有代表性的问题，覆盖不同业务主题、问法、语言和难例。每条包括：

```json
{
  "id": "faq-providers",
  "question": "本项目支持哪些 chat provider？",
  "relevantDocIds": ["project-faq.md"]
}
```

被标注文档需要事先入库，而且评测请求与入库请求必须属于同一租户。黄金集由 `/eval/retrieval` 的请求体传入，服务端不会自动加载或自动入库。

### 2.3 查询命令

```bash
curl -s -X POST 'http://localhost:8080/eval/retrieval' \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{
        "topK": 5,
        "cases": [
          {
            "id": "faq-providers",
            "question": "本项目支持哪些 chat provider？",
            "relevantDocIds": ["project-faq.md"]
          },
          {
            "id": "eval-temperature",
            "question": "Judge 使用的 temperature 是多少？",
            "relevantDocIds": ["eval-spec.md#3"]
          }
        ]
      }' | tee retrieval-report.json | jq \
      '{cases, recallAtK: .avgRecall, precisionAtK: .avgPrecision, meanMrr, hitRate, totalDurationMs}'
```

响应里的 `avgRecall` 就是该测试集的平均 Recall@K。为了能够复现，报告中还应记录：

- 黄金集版本和用例数量
- `topK`
- embedding、chunking、rerank、混排权重等配置
- 知识库数据快照或版本
- 测试租户和运行时间

简历写法示例：

> 构建 50 条人工标注检索黄金集，在固定知识库快照上将 RAG Recall@5 从 82% 提升至 91%。

不能只写“RAG 召回率 91%”，因为没有 K 值、用例数和数据口径时无法验证。

## 3. NL2SQL 成功率

NL2SQL 至少要区分“SQL 执行成功”和“查询结果正确”。简历优先使用结果正确率。

### 3.1 SQL 执行成功率

```text
执行成功率 = 成功产生并执行 SQL 的问题数 / 合法问题总数
```

本项目 `POST /analytics/sql`（也可使用 `/chat/sql`）的响应中：

- `sql != null`：本轮至少有一次 SQL 成功执行。
- `sql == null`：没有成功执行 SQL。
- `rows=[]`：可能是合法的空结果，不能直接判为失败。
- `guardBlocked=true`：本轮至少有一次 SQL 被护栏拒绝；模型后续可能已经自修复并成功，因此也不能直接判为失败。

所以受控测试中的执行成功条件建议定义为：

```text
HTTP 为 2xx 且响应 sql 不为 null
```

单条查询示例：

```bash
curl -s -X POST 'http://localhost:8080/analytics/sql' \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"question":"上月退款金额最高的 5 个客户是谁？"}' |
  jq '{sql, rowCount, rows, guardBlocked}'
```

### 3.2 结果正确率（推荐）

```text
NL2SQL 结果正确率 = 返回结果与黄金答案等价的问题数 / 黄金集问题总数
```

黄金集建议包含：

```json
{
  "id": "refund-top5",
  "question": "上月退款金额最高的 5 个客户是谁？",
  "tenant": "acme",
  "expectedRows": [
    {"customer_id": "c01", "refund_amount": 1200.00}
  ]
}
```

判定时应比较标准化后的结果集，不建议要求 SQL 文本完全相同，因为不同 SQL 可能语义等价。标准化规则需要事先固定：

- 金额、百分比和时间的精度及容差
- 是否忽略行顺序；Top-N 查询通常不能忽略顺序
- 列名映射和空值处理
- 相同问题使用固定数据库快照、时区和租户

简单的标量/固定字段可以直接借助项目已有的通用评测端点：

```bash
curl -s -X POST 'http://localhost:8080/eval/run' \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{
        "targetBaseUrl": "http://edge-gateway:8080",
        "cases": [
          {
            "id": "order-count",
            "endpoint": "/analytics/sql",
            "method": "POST",
            "body": {"question": "当前租户一共有多少订单？"},
            "expectedJsonPaths": {
              "$.rowCount": 1,
              "$.rows[0].total": 42
            }
          }
        ]
      }' | tee nl2sql-report.json | jq '{total, passed, passRate, durationMs}'
```

`passRate = passed / total`。复杂结果集建议由独立评测脚本调用 `/analytics/sql`，对 `rows` 做排序、类型和数值标准化后再与 `expectedRows` 比较。

项目现有 `deploy/smoke-nl2sql.sh` 主要验证接口和响应结构，不校验业务结果，不能把 smoke 通过率写成 NL2SQL 正确率。

简历写法示例：

> 建立 100 条 NL2SQL 业务黄金集，在固定数据库快照上实现 94% SQL 执行成功率、89% 结果正确率。

## 4. P95 响应时间

### 4.1 计算方式

采集同一口径下的 `N` 个端到端响应时间并升序排列，最近秩定义为：

```text
P95 = sorted_latency[ceil(0.95 × N)]
```

数组下标从 0 开始实现时需要再减 1。不同统计工具可能使用插值或直方图估算，因此同一份报告应固定工具和版本。

### 4.2 推荐查询方式：k6 压测

示例脚本：

```javascript
import http from 'k6/http';
import { check } from 'k6';

export const options = {
  scenarios: {
    rag: {
      executor: 'constant-vus',
      vus: 20,
      duration: '5m',
    },
  },
  thresholds: {
    http_req_duration: ['p(95)<2000'],
    http_req_failed: ['rate<0.01'],
  },
};

export default function () {
  const response = http.post(
    `${__ENV.BASE_URL}/rag/query`,
    JSON.stringify({query: '退款规则是什么？', topK: 5}),
    {
      headers: {
        Authorization: `Bearer ${__ENV.ACCESS_TOKEN}`,
        'Content-Type': 'application/json',
      },
    },
  );
  check(response, {'HTTP 200': (r) => r.status === 200});
}
```

执行：

```bash
BASE_URL=http://localhost:8080 \
ACCESS_TOKEN="$ACCESS_TOKEN" \
k6 run rag-p95.js
```

k6 汇总中的 `http_req_duration p(95)` 是端到端 P95。正式数据应先预热，再单独运行测量阶段，并记录：

- 测试接口和请求类型
- VU、QPS、持续时间和总请求数
- 文档/数据库数据规模
- 冷缓存还是热缓存
- 是否包含网关、RAG、LLM 等完整链路
- 错误率；不能通过丢弃超时请求美化 P95
- 运行机器、模型服务和网络环境

简历写法示例：

> 在 20 VU、持续 5 分钟的端到端压测下，将 `/rag/query` P95 从 2.4 s 降至 1.6 s，错误率低于 1%。

### 4.3 Prometheus 查询

当前各服务只有 Actuator 依赖，仓库中没有 `micrometer-registry-prometheus`；部分 `application.yml` 虽暴露了 `prometheus`，也不足以生成 Prometheus 抓取端点。`edge-gateway` 和部分服务的暴露列表同样未包含 `prometheus`。因此目前不能把下面的 PromQL 当作已经可用的查询。

补齐 Prometheus registry、暴露 `/actuator/prometheus`，并为 `http.server.requests` 开启 percentile histogram 后，可按接口查询：

```promql
histogram_quantile(
  0.95,
  sum by (le) (
    rate(http_server_requests_seconds_bucket{
      application="knowledge-service",
      uri="/rag/query",
      method="POST"
    }[5m])
  )
)
```

实际标签应以 `/actuator/prometheus` 输出为准；如果没有设置 `application` 公共标签，就不能直接使用上面的 `application` 过滤条件。

`/eval/retrieval` 返回的 `results[].durationMs` 也可以计算一组顺序评测请求的 P95：

```bash
jq '
  [.results[].durationMs] | sort |
  . as $values |
  $values[((($values | length) * 0.95 | ceil) - 1)]
' retrieval-report.json
```

但它不是并发压测，应该称为“评测集查询耗时 P95”，不能用来证明生产容量。

## 5. L1 语义缓存命中率

### 5.1 计算方式

```text
缓存命中率 = hit / (hit + miss)
```

- `hit`：缓存开启、问题有效，并且最高相似度大于等于阈值后直接返回缓存答案。
- `miss`：缓存开启、问题有效，但没有合格条目，继续执行 RAG/LLM 并回填。
- `bypass`：缓存关闭或问题为空，建议不放入分母。
- `error`：embedding/Redis 异常，单独统计，不应悄悄算作 hit。

本项目的 L1 语义缓存位于 `/chat` 的 RAG/LLM 之前，当前配置默认开启，阈值默认 `0.95`，默认使用 Redis 存储。`SemanticCache` 目前只输出 debug 级命中日志，没有 hit/miss Micrometer 计数器；Redis 中的 key 或条目数量只是缓存容量，不是命中率。

### 5.2 当前可做的受控测量

1. 清空测试租户的缓存，准备一组固定问题。
2. 第一轮请求用于预热。
3. 第二轮发送相同问题或预先定义的同义问题。
4. 开启 `SemanticCache` debug 日志，统计第二轮的 `semantic cache hit` 条数。
5. 因为测试脚本知道第二轮有效请求总数，所以：

```text
受控命中率 = debug 命中日志数 / 第二轮有效请求数
```

该方法只适合一次性实验。通过响应时延猜测是否命中并不可靠。

### 5.3 推荐的生产埋点

为缓存请求增加低基数 Counter：

```text
conversation.semantic.cache.requests{result="hit"}
conversation.semantic.cache.requests{result="miss"}
conversation.semantic.cache.requests{result="bypass"}
conversation.semantic.cache.requests{result="error"}
```

PromQL：

```promql
sum(rate(conversation_semantic_cache_requests_total{result="hit"}[1h]))
/
sum(rate(conversation_semantic_cache_requests_total{result=~"hit|miss"}[1h]))
```

不要把 `tenantId` 直接作为 Prometheus label，否则租户增长会造成高基数。需要按租户分析时，应把明细写入日志、审计存储或分析数据库。

简历中要说明缓存类型，例如：

> 基于租户隔离的 L1 语义缓存将重复问答命中率提升至 68%，减少 55% 的下游 LLM 调用。

“命中率”和“LLM 调用减少率”是两个不同指标，应分别统计。

## 6. 租户数量

### 6.1 已注册租户数

启用 RBAC 管理面时，可以查询：

```bash
curl -s 'http://localhost:8080/auth/admin/tenants' \
  -H "Authorization: Bearer $ROLE_ADMIN_TOKEN" |
  jq '{registeredTenants: length, tenants: map(.tenant)}'
```

该接口要求 `role-admin` scope。JDBC 模式下，它最终来自 `USERS.TENANT` 的去重结果。也可直接查询 auth 数据库：

```sql
SELECT COUNT(DISTINCT TENANT) AS registered_tenants
FROM USERS
WHERE TENANT IS NOT NULL AND TENANT <> '';
```

这表示“至少有一个账号的已注册租户”，不是容量上限。

### 6.2 有知识文档的租户数

知识库 registry 使用 Redis 时，每个租户对应一个 `rag:docs:<tenantId>` Hash。生产环境使用 `SCAN`，不要使用阻塞式 `KEYS`：

```bash
redis-cli --scan --pattern 'rag:docs:*' |
  sed 's/^rag:docs://' |
  sort -u |
  wc -l
```

这只统计有文档登记记录的租户。公共知识库保留租户 `__public__` 是否计入，需要在口径中明确；通常统计业务租户时应排除它：

```bash
redis-cli --scan --pattern 'rag:docs:*' |
  sed 's/^rag:docs://' |
  grep -v '^__public__$' |
  sort -u |
  wc -l
```

如果 registry 使用默认的内存实现，重启会丢失，而且没有面向生产的全局租户统计接口。

### 6.3 “支持 N 个租户”的正确证明方式

“已注册 N 个租户”和“系统支持 N 个租户”不是同一个指标。后者需要：

1. 创建 N 个合成租户，并为每个租户准备隔离的数据。
2. 按预计的活跃租户比例、QPS 和读写比进行压测。
3. 同时验证 P95/P99、吞吐、错误率、CPU、内存、连接池、Redis、向量库和数据库资源。
4. 加入跨租户负向用例，确认租户 A 无法读取租户 B 的文档、会话、SQL 数据和缓存。
5. 在预先定义的 SLO 内通过，才能把 N 写成“验证支持的租户数”。

推荐表达：

> 完成 500 个租户、50 个并发活跃租户的容量与隔离测试，在目标负载下 P95 小于 1.8 s，未发现跨租户数据泄漏。

仅统计 `USERS` 或 Redis key 数量时，应写“管理/承载 N 个已注册租户”，不要写“支持 N 个租户并发”。
