4. **实现受限业务范围的 NL2SQL 与订单查询。** 明确订单查询直接调用参数化业务接口；统计分析向模型提供白名单表结构、字段注释及枚举值，生成 SQL 后校验只读语句、访问表和租户条件，通过只读账号、行数限制及执行超时约束查询；将执行错误反馈给模型进行有限次数修复。基于固定种子库构建 150 条问数用例，以结果等价性判定正确性，最终执行成功率 **99.3%**、结果正确率 **95.3%**。

## 三、架构与业务落地问答

### 3. 为什么同时使用业务网关和 LiteLLM？

**面试回答：** 我把业务身份管理与模型调用管理分开。业务网关解决谁能访问哪个接口、属于哪个租户以及允许多大流量；LiteLLM 解决使用哪个真实模型、请求发往哪个供应商，以及上游失败后的回退。Java 和 Python 服务使用逻辑模型名调用统一接口，更换供应商主要修改网关配置。

```text
用户 → 业务网关 → 对话服务 / AgentScope / 数据分析服务
                         ├─ 知识库、订单、工作流等业务服务
                         └─ LiteLLM → 模型供应商
```

两个网关不是所有请求都必须经过的两级串行代理。明确订单查询可以直接查询订单服务，不调用模型。

业务网关校验外部凭据并换发短时内部 JWT，模型不能通过工具参数覆盖可信租户、用户和权限。Java 领域服务保留数据、事务和业务副作用的管理职责。

### 4. 模型网关接入中有什么实际问题？

**有仓库依据的问题和设计：**

- 接口兼容不代表模型能力等价。配置记录了 AgentScope 混合消息内容与 Ollama 原生适配器的兼容问题，采用 OpenAI-compatible 接口接入。备用模型在工具调用、结构化输出、上下文长度方面也可能与主模型不同。
- 多层重试会放大延迟。应用客户端、LiteLLM、Agent 循环都有再次调用的可能，需要一起分配重试和超时预算，通过上游冷却、请求截止时间、执行步数限制控制放大。
- 备用模型返回 HTTP 成功，不代表任务完成。应验证工具调用、结构化输出和最终结果，不能只观察可用性。

**边界：** 将配置和防护设计描述为工程实践；只有本人参与且有记录的故障，才作为个人亲历事故讲述。

### 5. 知识问答怎么落地？检索效果不好如何排查？

**面试回答：** 以查询退款规则为例，文档经过解析、分块和索引写入，保留来源信息。查询时召回相关片段、融合过滤并按上下文预算交给模型，回答携带来源标识。

| 现象 | 排查位置 | 处理方向 |
| --- | --- | --- |
| 正确文档没有召回 | 原文解析、分块、索引、召回 | 修正文档处理和召回策略 |
| 正确文档排名靠后 | 候选重复、融合和排序 | 分析源内排名与融合策略 |
| 正确片段已注入但回答错误 | 实际上下文、截断、提示词、模型 | 调整上下文与回答约束，评估模型能力 |

不能所有问题都归结为 Prompt。也不能把引用 ID 存在等同于引用内容支持答案。

### 6. NL2SQL 的完整链路是什么？SQL 能执行就算成功吗？

**面试回答：** 不算。语法正确、数据库执行成功、结果符合业务口径是三个层次。例如“销售额”是否扣除退款、按下单还是支付时间统计，口径错误也可能生成合法 SQL。

当前链路：

1. 提供白名单表结构、字段注释及关键枚举值。
2. 模型通过 `run_sql` 提交 SQL。
3. Java 校验只读语句、表范围和租户条件。
4. 使用只读账号执行，限制行数和执行时间。
5. 校验或执行失败时反馈错误，允许模型有限次数修复。
6. 返回 SQL、真实结果和解读；对解读中无法在结果中找到的数字作告警。

当前数字核对是告警机制，不是完整的业务语义验证或强制阻断。

**已有评测问题：** 订单金额口径、Top 客户筛选、聚合结果错误。因此同时统计最终执行成功率与结果正确率，不能只统计 HTTP 200。

**改进方向：** 歧义问题补充指标定义或请求澄清。完整指标语义层不能作为当前已完成功能宣称。枚举信息可减少猜测，但现有对照没有证明引入枚举后效果提升了某个固定百分点。

### 7. 智能客服做到什么程度？

更准确的项目定位是“知识问答与业务查询助手”。可以说明的场景包括：

- “退款规则是什么”：检索知识库后回答。
- “查询订单 101”：提取订单号并查询权威订单服务。
- “查一下我的订单”：没有订单号时提示补充。
- “统计订单数据并分析”：通过 NL2SQL 或 Agent 分析入口处理。
- 涉及写操作：按工具权限、精确参数确认和业务流程执行。

**实现边界：** `/chat/auto` 有订单确定性快路径和 RAG 分流，并未将所有复杂问题自动转交 Agent；其他 `TOOL` 分类也不能一概描述成已经执行工具。人工坐席接管、坐席分配、客服解决率需要独立业务实现和运营数据，不能从当前能力推导。

## 四、文档版本、检索与评测问答

### 9. 怎么保证文档是最新版本？

先定义“最新”：保证知识库中最新发布成功的版本，不等于自动知道外部源文件的最新变化。源文件更新还需同步任务、变更通知或重新上传发现。

```text
提交 v2 → 解析与分块 → 写入各索引并记录状态
        → 完成前置处理 → 原子提交注册表有效版本
        → 查询过滤非有效版本 → 旧版本延后清理
```

若 v1 已发布、v2 向量写入成功但 ES 失败，有效版本仍为 v1；带版本的 v2 候选会被过滤。失败任务重试，稳定片段 ID 支持重复写入。Redis Lua 原子校验版本递增，避免旧任务覆盖有效版本。

**需要讲清的边界：**

- 写入确认不一定代表立刻可搜索，发布门槛还应考虑搜索可见性。
- 先召回再过滤可能让旧版本占用名额，需扩召、清理或下推版本约束。
- 答案缓存可能保留旧规则，需缓存失效或知识库版本绑定，不能只更新索引。
- 当前版本过滤放行缺少 `docId/version` 的候选，一些关键词和图谱候选没有完整版本元数据。准确表述是“已实现可靠入库链路的版本发布与带版本候选过滤”，不能宣称所有召回源全链路严格最新版。

### 10. 文档召回分几步？

```text
问题与可信身份
  → 可选查询扩展
  → 并发向量、关键词、BM25、图谱召回
  → 去重与融合
  → 有效版本过滤
  → 文档权限过滤（enforce 模式）
  → 重排或直接截断
  → 返回 Top-K
  → 对话侧按上下文预算组装片段
  → 模型生成回答
```

权限过滤应该在候选交给外部重排/生成模型前完成。当前细粒度授权默认关闭；只有 enforce 模式真正过滤，shadow 只观察，不可混称为已启用严格授权。

### 11. 初始召回多少、最终保留多少？

需要区分三种数量：各路初始候选数、检索接口最终返回数、实际进入模型的片段数。

**代码默认值与生效条件：**

- 检索 `topK` 默认 5。
- 重排候选放大倍数默认 3；实际启用使用该倍数的重排器时，基础召回限额为 15。
- 多查询变体、租户库与公共库可能分别召回；关键词和图谱还有各自配置。因此 15 不是融合后的总候选上限。
- 授权开启时取重排与授权扩召倍数的最大值，不直接相乘，并限制计算得到的基础限额；不能把它解释成所有来源合并后的严格总量上限。
- 对话侧默认请求 5 个片段，再按 4,000 字符预算截断。字符数不是精确 Token 数，实际进入模型的片段可能少于 5。
- 支持重排分数阈值，但默认值为零；不能宣称默认配置已经实现有效的低相关性拒答。

这些是配置默认值，不是每次部署的实际生效值。关闭重排时的候选策略也会不同。

### 12. 为什么是这些数量？如何调参？

**面试回答：** 5 和 15 是初始配置，是否合理需要用固定评测集验证。候选数控制覆盖与重排成本，最终片段数控制证据覆盖与上下文噪声。

**建议实验，非已完成结果：**

1. 固定模型、语料、分块和其他配置，比较不同候选规模的 Recall、重排延迟与成本。
2. 比较最终保留 3、5、8 等数量时的答案正确性、证据覆盖与输入 Token。
3. 分开观察单文档事实题和多文档综合题。
4. 选择质量增益开始收敛、成本仍可接受的位置。
5. 权限过滤后不足 Top-K 时允许少返回，不能为凑数补入无关或未授权内容。

不能声称项目已经对这些参数完成全面搜索。

### 13. 为什么不用归一化，而用 RRF？

**面试回答：** 归一化把数值放到相近范围，但不能让不同检索器的分数具有相同含义。BM25 的 0.9 和向量的 0.9 并不代表同样的相关性。

按最大值归一化时，`20、18、2` 和 `2、1.8、0.2` 都变成 `1、0.9、0.1`。它不能校准跨查询或跨检索器的相关程度，结果集合变化也可能改变归一值。

RRF 的计算方式：

```text
RRF(d) = Σ 1 / (c + rank_s(d))
```

其中 `s` 是召回源，项目常数 `c` 默认 60，与返回数量 Top-K 不同。

优点：无需先校准原始分数；多源靠前的候选累积贡献；新增或替换召回源时对分数分布变化较不敏感。

代价：丢失分数差距；弱召回源的第一名仍会得到较高贡献；高度相关的召回源可能重复强化同类信号。需要做消融实验，不能说 RRF 总是优于归一化或学习排序。

**指标归因：** 80.0%→98.5% 是“向量单路”与“四路召回加 RRF”的整体对照，不是只替换融合算法的结果。证明 RRF 更优需要保持候选源等条件不变，仅替换融合策略。

### 14. 检索准确率怎么评判？

| 层面 | 指标 | 含义 |
| --- | --- | --- |
| 召回覆盖 | Recall@K、Hit@K | 需要的证据是否找到 |
| 候选纯度 | Precision@K | 返回内容中相关内容的比例 |
| 排名 | MRR、nDCG@K | 相关内容是否靠前 |
| 回答 | 正确性、证据支持度、完整性 | 最终回答是否正确、有依据且完整 |
| 工程表现 | 延迟、成本、失败率 | 效果是否值得代价 |

当前 200 题每题标注一个相关文件，Top-10 命中该文件任意片段即算成功，所以文件级 Recall@10 等同 Hit@10。98.5% 表示 197 题找到标注文件，不等于 98.5% 的答案正确。

局限：正确文件中的片段未必能回答问题；单相关文件标注可能漏掉其他合理来源；引用 ID 可回溯不等于支持答案；模型自评通过不等于独立业务验收。

现有引用 ID 有效率为 35/39=89.7%，不能表述为事实准确率。现有评测没有实测 Jina Reranker，检索提升不能归因于 Jina 重排。

### 15. 黄金集怎么设计？

**当前已做：** 从 20 份项目文档生成 200 个问题，保留来源与参考答案，校验来源信息。属于项目文档合成评测集，不能称为全量人工审核的生产黄金集。

**更完整的设计建议：**

| 字段 | 用途 |
| --- | --- |
| 问题和业务场景 | 确定任务类型 |
| 租户、角色、查询时间 | 确定可见范围与生效版本 |
| 是否可回答 | 有依据、信息不足或需要澄清 |
| 相关文档及版本 | 标识权威来源 |
| 证据片段 | 支持答案的具体内容 |
| 必答事实 | 评价完整性 |
| 禁止结论 | 识别过期规则、越权内容和无依据承诺 |

覆盖直接事实、同义改写、缩写口语、多条件、跨文档、新旧版本冲突、相似干扰、无答案、无权限和缺参数问题。

模型可以辅助出题，但来源、证据和答案需人工审核；关键样本双人独立标注并处理分歧。合并多个检索器的候选后标注，可减少对单一检索器的偏好。

调参集和测试集按文档或主题隔离，避免同题改写跨集泄漏；这不意味着从检索库删除测试所需文档。每次评测冻结语料、Embedding、分块和配置版本，保留失败样例。

## 五、多任务编排与长任务问答

### 16. 多任务怎么拆？为什么需要多 Agent？

**面试回答：** 按信息依赖和可验证产出拆分，不按角色名字凑 Agent 数量。简单订单查询直接调用接口；复杂目标只有存在可独立获取的信息或处理步骤时才拆分。

以下是说明性例子：分析本月退款情况，结合退款制度给出建议。

| 任务 | 产出 | 依赖 |
| --- | --- | --- |
| A：确认统计口径和表结构 | 时间、口径、可用字段 | 无 |
| B：检索有效制度 | 规则与来源 | 无 |
| C：查询退款统计 | SQL、真实数据、范围 | A |
| D：分析并提出建议 | 有数据与规则依据的结论 | B、C |

每个节点需要明确输入、输出、完成条件。需要频繁共享中间状态的步骤不宜过度拆分，否则模型调用和上下文传递成本可能超过并行收益。

### 17. 当前 DAG 怎样执行？有哪些限制？

- Planner 输出结构化任务和依赖，默认最多 6 个任务。
- 实现重复 ID、环等校验；未知依赖当前有兼容旧 Java 的忽略行为，不能宣称所有无效依赖都严格拒绝。
- 按拓扑分层，同层有界并行，下游使用直接依赖结果，最后 synthesis 汇总。
- 当前是层级屏障调度：同层全部结束才进入下一层。即使某个下游的依赖先完成，也可能等待同层无关慢任务。
- 后续可改为依赖满足即调度，但不是当前已实现能力。
- 当前重规划重新执行修订后的 DAG，不能说只重跑失败节点或自动复用全部已完成节点。
- worker 的 ERROR/TIMEOUT 结果不能当成成功；汇总需说明限制。基础设施异常可能使请求整体失败。

### 18. Critic/Replan 一定改善效果吗？

不一定。模型自评是运行反馈信号，不是独立验收结果。

现有 20 题测试中，关闭重规划的规则覆盖率为 70%，开启为 75%，但开启后 P95 从约 48.8 秒升至 140.3 秒，并出现一次 HTTP 500。因此只能说明实现了反馈与重规划能力，不能宣传为显著、稳定提升任务完成率。

应设置重规划次数、步数、时间和 Token 预算，并用独立验收标准比较效果与成本。

### 19. 长任务怎么拆？

优先选择可保存、可验证、可单独重试的产出边界，比如检索证据、保存引用、查询统计、保存数据、生成报告。避免只有一个长循环，没有中间产物。

| 问题 | 机制 |
| --- | --- |
| 请求耗时过长 | 异步提交与任务查询 |
| 页面断连后丢失进度 | 持久事件与 SSE 续订 |
| 进程崩溃后继续执行 | 检查点、恢复协议及幂等 |

SSE 恢复的是观察进度，不是执行现场。

### 20. 工具调用成功，但检查点保存前崩溃怎么办？

**面试回答：** 这个窗口不能靠检查点消除。恢复可能再次调用工具，写操作需要业务接收方用稳定幂等键识别重复请求，必要时先查操作状态。租约和 CAS 协调执行权及状态更新，业务幂等处理重复副作用。

不能将“有 Redis 锁或检查点”表述为端到端 exactly-once。外部支付等系统仍需自己的幂等与状态查询协议。

### 21. 当前项目能恢复所有异步任务吗？

不能这样宣称。目前需要区分：

- 中央任务服务管理异步状态、租约、取消与持久事件。
- 独立 session 接口提供完整工具结果边界的检查点和恢复。
- 当前异步 DAG 不能由此推导为已经实现跨进程自动续跑；中央异步执行闭包丢失时，存在明确标记孤儿任务失败的路径。
- 恢复要重新验证身份、权限与有效期；检查点不长期保存调用方令牌。涉及副作用的恢复还需要原幂等键和新的确认凭证。

## 六、面试前核对清单

- 区分已经实现、默认配置、实际启用、实际验证、未来改进五种状态。
- 不把防护设计自动写成亲历生产事故，不把个人项目归入雇主商业项目。
- 不把文件级命中率说成最终回答正确率。
- 不把多路融合整体收益全部归因于 RRF 或重排。
- 不把本地各 5 次拓扑测试描述成生产 SLA 或稳定容量提升。
- 不把 SQL 最终执行成功率说成首次生成成功率。
- 不把 SSE 续订、任务持久化和完整执行恢复混为一谈。
- 不宣称所有召回源已严格执行最新版过滤。
- 不宣称没有开展过的模型微调、生产部署或运营效果。
