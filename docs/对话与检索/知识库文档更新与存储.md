# 知识库文档更新与存储

本文说明 `knowledge-service` 中文本文档如何更新、新旧版本如何替换、哪些字段会变化，以及一篇文档最终写入哪些存储。
接口的基础用法见 [RAG 接入指南](rag-guide.md)，数据库连接信息见
[数据存储清单](../参考/databases.md)。

> 本文聚焦由 `DocumentService` 管理的文本、PDF、Office、Markdown 等文档。
> 图片走独立的多模态向量链路，更新语义不同，见[图片文档的区别](#8-图片文档的区别)。

## 1. 核心结论

项目没有独立的 `PUT` 或 `PATCH` 更新接口。更新仍通过：

```http
POST /rag/documents
```

系统使用“租户分区 + 文件名或 JSON `title`”确定文档身份：

```text
docId = SHA-256(tenantId + ":" + displayName) 的前 16 个十六进制字符
```

因此，同一租户内以相同文件名或 `title` 重新上传，才会命中旧文档并更新：

```text
同租户 + 同 displayName
  → docId 不变
  → 清理旧文档的派生数据
  → 用新正文全量重新切片和建索引
  → version + 1
```

当前更新不是正文差异合并，也不是只更新发生变化的 chunk，而是整篇文档全量重建。

核心代码：

- 入口：`knowledge-service/.../controller/DocumentController.java`
- 生命周期：`knowledge-service/.../lifecycle/DocumentService.java`
- 文档元数据：`knowledge-service/.../lifecycle/DocumentInfo.java`

## 2. 更新请求参数

### 2.1 Multipart 文件

```http
POST /rag/documents
Content-Type: multipart/form-data
```

| 参数 | 必填 | 含义 |
|---|---:|---|
| `file` | 是 | 新的完整文件内容；原文件名作为 `displayName` |
| `category` | 否 | 文档分类；用于检索过滤 |
| `visibility` | 否 | 缺省为当前租户；`public`/`shared` 写公共分区 |

示例：

```bash
curl -s -X POST 'http://localhost:8080/rag/documents' \
  -H 'X-Api-Key: dev-key-acme-ingest' \
  -F 'file=@./guide.md' \
  -F 'category=manual'
```

文件由 `DocumentTextExtractor` 提取文本。`contentType` 和原始字节数由
`MultipartFile` 提供，不需要调用方单独填写。

### 2.2 JSON 文本

```http
POST /rag/documents
Content-Type: application/json
```

| 参数 | 必填 | 含义 |
|---|---:|---|
| `title` | 是 | 文档显示名，也是同名覆盖的身份参数 |
| `text` | 是 | 新的完整正文 |
| `contentType` | 否 | 默认 `text/plain` |
| `category` | 否 | 文档分类；不传或传空会清除旧分类 |
| `visibility` | 否 | body 中优先；也可使用 query 参数 |

示例：

```bash
curl -s -X POST 'http://localhost:8080/rag/documents' \
  -H 'X-Api-Key: dev-key-acme-ingest' \
  -H 'Content-Type: application/json' \
  -d '{
    "title": "guide.md",
    "text": "这是 guide.md 的新版本。",
    "contentType": "text/markdown",
    "category": "manual"
  }'
```

### 2.3 什么情况不是更新

| 操作 | 实际结果 |
|---|---|
| 修改文件名或 `title` 后上传 | 新建文档；旧文档继续存在 |
| 另一个租户上传同名文档 | 新建该租户自己的文档 |
| 从租户库改为 `public/shared` | 在公共分区新建文档，不会迁移或删除租户库旧文档 |
| 正文完全相同但同名重传 | 仍执行全量重建，版本仍加一 |

当前没有内容 hash 去重、重命名接口、移动可见性接口或只修改分类的接口。

## 3. 更新权限

Controller 先检查写入 scope：

- 当前租户文档：需要 `ingest`
- 公共/共享文档：需要 `public-ingest`

如果同名文档已存在，并且启用了文档级授权，覆盖前还会检查当前用户是否有该文档的 `edit` 权限。
没有权限时返回 `403`，不会先删除旧内容。

同名覆盖只替换内容和索引，不调用 `onDocumentDeleted()` 或
`onDocumentCreated()`，因此原 SpiceDB owner、home department 和分享关系保持不变，上传者不能通过同名覆盖夺取所有权。

## 4. 哪些字段会更新

`DocumentInfo` 是文档级目录记录：

```java
record DocumentInfo(
    String docId,
    String tenantId,
    String displayName,
    String contentType,
    long sizeBytes,
    int segmentCount,
    int version,
    Instant uploadedAt,
    String category
) {
}
```

### 4.1 保持不变

- `docId`：同租户、同 `displayName` 时保持稳定
- `tenantId`：仍在原分区内更新
- `displayName`：因为同名才会命中更新
- 已有授权关系：owner、部门和分享关系不重建

### 4.2 覆盖或重新计算

| 字段或数据 | 更新方式 |
|---|---|
| 正文 | 被本次完整正文替换 |
| `contentType` | 使用本次请求或文件的 MIME |
| `category` | 使用本次请求；空值会清除旧分类 |
| `sizeBytes` | 文件取原始文件大小；JSON 取正文 UTF-8 大小 |
| `segmentCount` | 根据新正文重新切片后计算 |
| `version` | 旧版本加一；首次上传为 1 |
| `uploadedAt` | 更新为本次上传时间 |
| chunk 文本 | 全量重新切分和增强 |
| embedding | 每个新 chunk 全量重新计算 |
| ES 全文索引 | 旧 chunk 删除后重新建立 |
| GraphRAG | 旧三元组清理后重新抽取 |

每个新 chunk 会携带：

```text
tenantId
docId
displayName
file_name
version
category（有值时）
index（切片序号）
```

## 5. 新旧文档替换流程

`DocumentService.upload()` 的实际顺序是：

```text
1. 校验 displayName 和正文
2. 确定租户或公共分区
3. 计算稳定 docId
4. 从 DocumentRegistry 查询旧 DocumentInfo
5. 对已有文档检查 edit 权
6. deleteInternal(oldInfo) 清理旧派生数据
7. nextVersion = oldVersion + 1
8. 用新正文建立 Document 和 metadata
9. 按当前配置重新切片
10. 可选 Contextual Retrieval 增强每个 chunk
11. 重新计算所有 embedding
12. 写向量库、DocumentMirror、ES 和 GraphRAG
13. 用相同 docId 覆盖 DocumentRegistry 元数据
14. 记录上传审计
15. 尽力失效 conversation-service 语义缓存
```

### 5.1 旧版本具体删除什么

`deleteInternal()` 清理以下数据：

| 存储 | 删除条件或来源键 |
|---|---|
| 向量库 | metadata 中 `tenantId` 和 `docId` 同时相等的全部 chunk |
| `DocumentMirror` | JVM 内相同 `tenantId + docId` 的全部明文 chunk |
| Elasticsearch | 按 `tenantId + docId` 执行 `_delete_by_query` |
| GraphRAG | 删除 `sourceId` 以 `displayName + "#"` 或 `docId` 开头的三元组 |

更新过程中不会先删除 Registry 记录；新文档所有主要写入完成后，
`registry.put(newInfo)` 使用同一个 `docId` 覆盖旧元数据。

### 5.2 新版本重新写什么

```text
新完整正文
  → DocumentSplitterFactory
  → ContextualEnricher
  → EmbeddingModel
  ├─ EmbeddingStoreRouter
  ├─ DocumentMirror
  ├─ SegmentIndexer / Elasticsearch
  └─ GraphIngestor
  → DocumentRegistry
```

切片策略支持：

- `recursive`
- `markdown-header`
- `parent-child`
- `semantic`

服务级配置主要包括：

```text
app.rag.chunking.strategy
app.rag.chunking.unit
app.rag.chunking.max-size
app.rag.chunking.overlap
app.rag.chunking.min-section-size
app.rag.chunking.parent.*
app.rag.chunking.semantic.*

app.rag.contextual.enabled
app.rag.contextual.max-doc-chars

app.rag.embedding.provider
app.rag.embedding.model-name
app.rag.embedding.dimensions
```

修改这些配置不会自动重建历史文档。要让历史文档使用新的切片或 embedding 配置，需要逐篇重传或另外实现批量重建任务。

## 6. 文档存储位置

一篇文本文档会扇出到多处存储，而不是只写一个数据库。

| 存储 | 保存内容 | application.yml 当前默认 |
|---|---|---|
| 向量库 | embedding、chunk 正文、chunk metadata | Qdrant |
| Document Registry | 文档级元数据和版本目录 | Redis |
| `DocumentMirror` | 明文 chunk，供内存关键词检索 | JVM 内存 |
| Elasticsearch | chunk 正文及 metadata，供 BM25 | ES 索引 `knowledge_segments_text` |
| GraphStore | GraphRAG 实体关系三元组 | MySQL `knowledge_graph` |
| auth-platform / SpiceDB | owner、部门、分享关系；不保存正文 | 默认授权模式 `disabled`，启用后写 |

### 6.1 向量库

默认配置：

```text
RAG_VECTOR_STORE_PROVIDER=qdrant
RAG_VECTOR_STORE_ISOLATION=collection-per-tenant
RAG_VECTOR_STORE_BASE_COLLECTION=knowledge_segments
```

每个租户一个 collection：

```text
knowledge_segments_<归一化tenantId>
```

其中保存每个 chunk 的向量、最终 chunk 文本和 metadata。公共库使用保留租户
`__public__` 派生自己的 collection。

可通过 `RAG_VECTOR_STORE_PROVIDER` 切换：

- `in-memory`
- `qdrant`
- `pgvector`
- `milvus`
- `chroma`
- `doris`

`collection-per-tenant` 模式下，这些后端分别使用每租户独立 collection、表或 namespace。

### 6.2 Redis Document Registry

默认 Redis 数据模型：

```text
key   = rag:docs:<tenantId>
type  = Hash
field = docId
value = DocumentInfo JSON
```

Registry 只保存文档级目录和版本信息，不保存原始正文。

配置为 `RAG_REGISTRY_STORE=in-memory` 时，Registry 改为进程内
`ConcurrentHashMap`，服务重启后文档列表会丢失；如果向量库仍是持久化后端，就可能出现“向量还能检索，但文档列表为空”。

### 6.3 JVM 内存明文镜像

`DocumentMirror` 按租户保存明文 chunk，供内存 keyword 分支使用。它没有持久化后端，也没有启动时从 Qdrant、Redis 或 ES 自动恢复的逻辑。

因此 knowledge-service 重启后：

- Qdrant 向量检索仍可使用历史数据
- Elasticsearch BM25 仍可使用历史数据
- Redis 文档列表仍可使用历史数据
- 内存 keyword 分支不再包含重启前的历史文档
- 重启后新上传或更新的文档会重新进入 `DocumentMirror`

### 6.4 Elasticsearch

默认索引：

```text
knowledge_segments_text
```

每条 ES 文档对应一个 chunk，主键为：

```text
tenantId/docId/index
```

保存字段：

```text
tenantId
docId
displayName
category
index
version
text
createdAt
```

文本使用配置的中文分析器（默认 `smartcn`）建立 BM25 倒排索引。

### 6.5 MySQL GraphRAG

默认数据库和表：

```text
database = knowledge_graph
table    = RAG_GRAPH_TRIPLE
```

保存：

- 主体和归一化主体 key
- 关系
- 客体和归一化客体 key
- `SOURCE_ID`
- `TENANT_ID`
- `CATEGORY`
- 创建时间

也可以使用 `RAG_GRAPH_STORE=in-memory`，此时三元组只存在 JVM 内存。

### 6.6 SpiceDB 授权关系

当 `app.rag.authz.mode=shadow|enforce` 时，新建文档会向外部
auth-platform/SpiceDB 写 owner、home department 等关系。分享和取消分享也更新这里。

它只保存授权关系，不保存正文、chunk 或 embedding。同名覆盖保留现有关系。

## 7. 原始文件是否保存

当前没有原始文件存储。

文本、PDF、Word、Markdown 等文件上传后：

```text
原始文件字节
  → DocumentTextExtractor / Apache Tika 提取文本
  → 切片
  → 保存 chunk 和派生索引
```

当前不会把原始文件或完整原文另存到：

- 本地文件系统
- MySQL 文档正文表
- MinIO
- S3
- 其他对象存储

持久化的是向量库和 ES 中的 chunk 文本、Redis 中的文档元数据，以及 GraphRAG 三元组。因此目前不支持下载原始上传文件，也不能保证从 chunk 无损还原原始排版。

如果需要原件下载、审计留档、OCR 重跑或更换 embedding 后离线重建，应增加
MinIO/S3 等原始文档存储，并在 Registry 保存对象 key、原件 hash 和处理状态。

## 8. 图片文档的区别

图片不会进入上述 `DocumentService` 文本生命周期。开启
`app.rag.multimodal-embedding.enabled` 后，图片由
`MultimodalRetrievalService` 直接生成 CLIP/jina-clip 向量，写入独立的：

```text
knowledge_images_<tenantId>
```

图片记录只带 `type=image`、`file_name`、`tenantId` 和 `mime` 等 metadata。
每次上传由向量库生成新记录 ID；当前没有基于同名图片的版本覆盖、图片 Registry 或 `/rag/documents/{docId}` 图片删除逻辑。

因此，同名图片再次上传会新增一条图片向量，而不是替换旧图片。

## 9. 一致性边界和风险

当前更新是“先删旧派生数据，再写新派生数据”，但 Qdrant、Redis、Elasticsearch、MySQL 和 SpiceDB 之间没有分布式事务。

### 9.1 更新中途失败

例如旧向量已删除，但新 embedding 调用失败：

- Registry 仍可能保留旧 `DocumentInfo`
- 旧向量已经不存在
- ES 或图谱可能已经被清理
- 用户列表仍能看到文档，但不同检索分支结果不一致

### 9.2 删除失败留下孤儿数据

当前工作树中的向量和图谱清理由 `deleteInternal()` 按尽力而为处理；失败时记录警告并可能留下旧向量或旧边。更新随后写入新版本后，旧数据可能与新数据一起参与召回。

ES 默认 `RAG_ES_FAIL_FAST=false`，ES 写入或删除失败会记录警告并继续；设置为
`true` 时异常会向上抛出，但仍不能回滚此前已完成的其他存储操作。

### 9.3 GraphRAG 异步竞态

启用 `RAG_GRAPH_ASYNC=true` 时，图谱抽取在异步线程执行。旧版本抽取任务如果尚未完成，可能在更新清理之后才写回旧三元组。

### 9.4 并发覆盖

当前没有 `If-Match`、文档版本条件更新或同 `docId` 分布式锁。两个请求同时覆盖同名文档时，都可能基于同一个旧版本计算 `nextVersion`，并在多个存储间交错删除和写入。

### 9.5 更稳妥的演进方向

对严格生产场景，建议改为版本化发布：

```text
写入完整 v2 到版本隔离的 sink
  → 校验向量、ES、图谱和 Registry staging 全部成功
  → 原子切换 activeVersion=v2
  → 失效缓存
  → 异步清理 v1
```

同时可增加：

- 原始文件对象存储
- 文档内容 hash 和幂等键
- `If-Match` 乐观锁
- 同 `docId` 分布式更新锁
- 跨存储 outbox/reconciliation 对账任务
- 从持久化存储恢复 `DocumentMirror` 的启动任务
- embedding/chunking 配置变更后的批量重建任务
