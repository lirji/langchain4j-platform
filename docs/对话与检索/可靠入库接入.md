# 可靠入库接入与迁移

生产文档新增和更新统一使用 `/rag/ingestions`。接口接收原文并创建持久化任务，返回 202；202 表示已接收，只有任务 READY 才表示已完成入库。查询只展示 Registry 已提交的版本。新版提交前，前一版本继续可查询。

## 两条路径的规则

| 场景 | 使用方式 |
|---|---|
| 生产新增/更新文本、PDF 等文档 | `POST /rag/ingestions`，multipart，显式文档 ID、版本与幂等键 |
| 本地演示或旧客户端迁移期 | `POST /rag/documents` 保留原同步请求和响应契约 |
| 同一生产知识库 | 关闭同步上传，禁止两个版本协议同时写入 |
| 旧图片上传、Obsidian 导入 | 生产旧写开关关闭时一并返回 404；v2 未提供对应批量/图片契约，不应自动改投 v2 |
| 删除、分享 | 网关有独立管理路由；生产 overlay 默认关闭管理写入口。分享可接受控 combined；现有同步删除没有与在途入库事务协调，执行删除前须暂停该文档写入并排空任务 |

`RAG_PRODUCTION=false`、`RAG_LEGACY_WRITE_ENABLED=true` 保留开发兼容。生产显式设置 `RAG_PRODUCTION=true`、`RAG_LEGACY_WRITE_ENABLED=false`。开关约束 `/rag/documents`、`/rag/image`、`/rag/obsidian/import` 的 POST，不隐藏文档读取、查询或分享接口。生产不允许同时启用旧写入口。

## 持久化与发布顺序

1. 备份任务库，使用 `database-migrations` 的 knowledge-ingestion 迁移，执行到 V9。V3 提供恢复字段，V9 增加可空 `PREPARATION_JSON`；历史迁移不修改。应用只校验/使用结构，不执行运行时建表。
2. 配置共享存储，确认 ingest-api、worker 与 query 使用一致的租户分区、向量集合、ES 索引及 Registry。
3. 暂停旧 worker 和旧同步写入，等待在途任务完成或其租约超时，再发布新 worker。迁移期间不混跑旧 worker：旧二进制不识别租约及 MANUAL_REVIEW。
4. 切换网关路由，再启用新入口。既有 docId 必须沿用 Registry 中的 ID；新文档版本从 1 开始，更新必须是已提交版本 + 1。
5. 回滚可以切换路由，但若已有 MANUAL_REVIEW 或租约任务，不得直接启动旧 worker；须先排空或经人工迁移任务状态，保留恢复字段及 V9 准备引用。

| 配置 | 生产要求 |
|---|---|
| `RAG_RUNTIME_ROLE` | combined 或 query / ingest-api / ingest-worker；combined 同样接受生产检查 |
| `RAG_INGESTION_STORE` | ingest-api / worker / combined 使用 `jdbc`，配置 `RAG_INGESTION_DB_*` |
| `RAG_SOURCE_STORE` | ingest-api / worker / combined 使用 `s3`，配置 bucket、endpoint/region 与独立权限 |
| `RAG_REGISTRY_STORE` | `redis`；Redis 持久化、备份与故障恢复由基础设施保证 |
| `RAG_VECTOR_STORE_PROVIDER` | query / worker / combined 使用持久化实现，例如 qdrant |
| `RAG_ES_*` | 混合查询要求 ES 查询开启；生产 worker / combined 启用 ES 时必须 `INDEX_ENABLED=true`、`FAIL_FAST=true` |
| `RAG_GRAPH_ENABLED` | 可开；query 角色开图检索时必须同时 `RAG_GRAPH_REQUIRE_PROVENANCE=true`，让图命中进入版本过滤与文档级判权 |

生产检查验证配置，不会验证 Redis AOF、存储备份或远端数据完整性。ingest-api 不执行 embedding，可保留其内部 in-memory 占位配置；query 不需要入库 JDBC/S3 写凭据。

`deploy/docker-compose.knowledge-production.yml` 可叠加基础 Compose 和 split Compose，提供入口与角色约束、网关拆分路由，并把原 `knowledge-service` 服务名转换为同数据面的只读兼容入口，避免内部客户端继续访问可同步写入的 combined。它不是可直接上线的完整生产部署：split 示例仍含开发账号、MinIO 和 hash embedding 默认值，必须按实际环境替换；公共组件优先复用 dev_infra，不应重复创建。

网关配置：`KNOWLEDGE_INGEST_URI` 指向 ingest-api，`KNOWLEDGE_QUERY_URI` 指向 query，`KNOWLEDGE_ADMIN_URI` 单独承接删除/分享。不设置专用 URI 时全部回退到原 `KNOWLEDGE_URI`，保持未拆分部署兼容。

## 客户端协议

```bash
curl -X POST "$EDGE/rag/ingestions" \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Idempotency-Key: import-orders-guide-v1' \
  -F documentId=orders-guide -F documentVersion=1 \
  -F displayName=orders.md -F category=manual -F file=@orders.md

curl "$EDGE/rag/ingestions/$JOB_ID" -H "Authorization: Bearer $TOKEN"
```

提交需要 `ingest` scope。响应带 `Location: /rag/ingestions/{jobId}`；客户端可轮询该地址。原有字段之外新增 `errorCode`、`failedStage`、`retryable`、`retryCount`、`nextRetryAt`，不返回原始异常。

- 同一租户、幂等键、提交者、文档 ID、版本、内容 SHA-256、文件类型、显示名和分类完全一致，返回原任务，包括已完成任务。traceId 不参与指纹。
- 相同键绑定不同内容或元数据返回 409；并发唯一键冲突后的返回路径也校验指纹。不同幂等键竞争同一文档版本同样冲突。
- 任务查询和重放仅允许原提交者；跨租户或其他用户返回 404。人工重试还要求 `ingest`，已有文档重新检查 edit 权限。
- 网络断开后使用同一幂等键重试，不生成随机新键。跨内容更新必须使用新幂等键和下一版本。
- 对象写入成功而数据库响应不确定时保留原文，避免误删并发获胜任务引用的对象。孤儿对象尚无自动清理器；清理必须核对任务引用并留出提交宽限期，不能对整个 source 前缀设置盲删生命周期。

## 恢复行为

默认最多自动重试 3 次（不含首次执行），间隔从 5 秒开始指数退避，上限 5 分钟。已成功的存储目标不重新执行。KDP-04 在首次写索引前把最终文本块、metadata、向量和文档信息持久化到 S3，并通过任务 revision/租约绑定引用；重试与重启只读取同一快照，不再次解析或调用 embedding。仅从未绑定结果、没有 sink 执行过的新任务允许重做准备。

| 状态/错误 | 行为 |
|---|---|
| PARTIAL / FAILED | 暂时依赖失败，等待 nextRetryAt 后恢复 |
| MANUAL_REVIEW / INVALID_INPUT_OR_PERMISSION | 参数、权限或版本提交错误，需要人工处理 |
| MANUAL_REVIEW / RETRY_EXHAUSTED | 达到自动重试上限，包括反复租约超时 |
| READY | 所有目标处理结束且必要目标成功，Registry 版本已提交 |

修复依赖或配置后，提交者可执行 `POST /rag/ingestions/{jobId}/retry`，返回 202。它恢复原任务并重置自动重试预算，不修改已绑定原文。任务处于运行或成功状态时返回 409；坏文件不能通过同键替换内容，需人工处理该文档版本占用后重新接入，当前没有自动废弃版本接口。

| env | 默认 |
|---|---|
| `RAG_INGESTION_MAX_RETRIES` | 3 |
| `RAG_INGESTION_RETRY_DELAY` | 5s |
| `RAG_INGESTION_MAX_RETRY_DELAY` | 5m |
| `RAG_INGESTION_PROCESSING_TIMEOUT` | 15m（执行租约） |
| `RAG_INGESTION_HEARTBEAT_INTERVAL` | 30s，必须小于租约的一半 |

worker 在解析之前抢占整条任务。心跳与阶段提交共用最新 revision；续期推进 revision，因此 reconciler 的旧快照不能覆盖已经续期的任务。超时旧 worker 在进入下一目标前会停止推进；已经发出的网络写入不能可靠撤销，仍依赖稳定版本主键与幂等存储操作。Registry 使用原子版本条件提交，旧版本不能回退可见性；这不是跨 JDBC、S3、Redis、向量库的分布式事务。

## 观测与验证

### 文档解析预算与错误分类（2026-10-19）

`app.rag.parsing.max-text-chars` / `RAG_PARSING_MAX_TEXT_CHARS` 默认 **2,000,000 字符**，必须大于零；包含解析器输出的空白。超过预算整份解析失败，不把截断正文写入索引。此预算只作用于文件文本提取，不覆盖旧 JSON 直接正文、上传大小、解压体积、页数、OCR、CPU 时间或进程内存。Docker 部署调整值时需向 worker/combined 容器显式传入该环境变量，宿主 `.env` 本身不等于容器环境。

| 任务 errorCode | 处理方式 |
| --- | --- |
| `DOCUMENT_EMPTY` | 无可抽取文本，人工确认是否为空文件或需要 OCR |
| `DOCUMENT_TEXT_LIMIT` | 正文超过预算；在资源评估后调整预算或拆分源文件 |
| `DOCUMENT_ENCRYPTED` | 提供经授权解密后的副本 |
| `DOCUMENT_PARSE_FAILED` | 文件损坏或无法解析，修正输入后重新接入 |
| `DOCUMENT_SOURCE_READ_FAILED` | 原文读取失败，沿用有限退避；耗尽后为 `RETRY_EXHAUSTED` |

前四类进入 `MANUAL_REVIEW`，不自动重试同一坏文件。该分类复用已有任务 `errorCode` 字段，不新增数据库迁移；原始异常只在服务端日志中记录。旧同步 `/rag/documents` 对输入错误仍返回 400，暂时读取故障返回 503，保留 `X-Error` 并附加稳定的 `X-Error-Code`；响应不包含底层异常或原文件名。

Markdown、父子及语义嵌套切分的最终 `index` 改为文档版本内唯一。Markdown 使用 CommonMark 0.25.1 识别顶层 ATX/Setext 标题，代码围栏、缩进代码和 HTML 内伪标题不形成章节；混合 H1/H2 正确重置路径。非标题正文不再把首行伪装为 `section`，原文首行代码缩进和行末空白保留。

发布这些切分规则前，应排空或隔离旧规则产生的在途/部分成功任务；旧任务应由原处理版本完成或经人工核对后恢复，避免跨规则重试混用向量/ES 分块。历史被覆盖的块须以新文档版本重新入库；本次代码发布不自动重建索引。持久化派生结果和阶段硬截止仍属于后续专项，详见[生产优化方案](知识库文档解析生产优化.md)。

- `knowledge.ingestion.jobs{status}`：任务库各状态数量。
- `knowledge.ingestion.oldest.pending.seconds`：最老未完成任务的年龄。
- `knowledge.ingestion.failures{stage}`：worker 各阶段失败次数，可结合处理量计算失败率。
- `knowledge.ingestion.stage.duration{stage,outcome}`：阶段耗时及成功/失败次数，可计算失败率。
- `knowledge.ingestion.commit.latency`：从接收到 READY 的总延迟。

计数/耗时指标由当前进程记录，状态与积压从任务库读取；指标不带租户或 jobId 标签。排障用 traceId 与服务日志。若启用通用 async-task 镜像，细粒度阶段与人工恢复状态仍以 `/rag/ingestions/{jobId}` 为准。

仓库验证：`mvn -o -pl knowledge-service,edge-gateway -am test`。覆盖幂等冲突、跨用户隔离、版本条件提交、租约续期与旧 worker 停止、退避上限、JDBC 恢复字段及网关路由。真实 MySQL/S3/Redis/向量库的断电恢复和吞吐压测需要在目标环境另行执行。


### 不可变准备结果（KDP-04）

- 默认对象路径为 `documents/prepared/<tenant>/<job>/v<version>/<sha256>/source`，复用原文 bucket，但使用独立前缀。内容与任务身份、原文指纹、schema 和处理版本绑定；校验大小、SHA-256、块/向量数量及维度。
- `RAG_INGESTION_PREPARED_MAX_BYTES` 默认 67,108,864（64 MiB），读写均受限；`RAG_INGESTION_PROCESSING_VERSION` 默认 `knowledge-prepared-v1`，生成行为变化时提升版本。旧快照不因当前配置/模型变化而重新生成。
- 缺失或临时 I/O：`PREPARED_RESULT_UNAVAILABLE` 有限退避；损坏/错配：`PREPARED_RESULT_INVALID`；超限：`PREPARED_RESULT_LIMIT`；不支持 schema：`PREPARED_RESULT_VERSION`；不安全旧任务：`LEGACY_PREPARATION_REQUIRED`。后四类进入人工处置，不悄悄重算。
- 迁移到 V9 后先停止旧 worker，再启动新 worker。没有准备标记的旧任务仅在 RECEIVED 且所有 sink PENDING 时自动接管；旧 PROCESSING/PARTIAL 即使被 reconciler 重置也不能证明没有副作用。不得把旧任务手动伪装成新 PENDING 来绕过检查。
- worker 需对原文与快照 `GetObject`，仅对 `documents/prepared/*` 增加 `PutObject`。split Compose 策略已同步；ingest-api 对快照前缀显式禁止 Put/Delete。自定义原文 prefix 时同步调整对应策略。已有对象不自动删除，未知绑定结果不能触发清理；保留期沿用原文/任务治理，孤儿清理须核对引用及提交宽限期。
- 回滚先停止消费并保留已绑定新任务，不能交给不理解快照的旧 worker；数据库扩展列不回删。实际迁移、IAM 策略发布、历史任务处置与重建索引需按目标环境发布流程执行，本次仅交付代码与验证。
- `python3 deploy/test-ingestion-prepared.py` 在 dev_infra 的随机 MySQL schema 与 S3 测试对象验证重建 worker 的恢复；使用已有本机私有凭据，只清理本测试资源。没有执行真实计费模型、线上迁移或断电灾备。
