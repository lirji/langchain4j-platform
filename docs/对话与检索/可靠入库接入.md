# 可靠入库接入与迁移

生产文档新增和更新统一使用 `/rag/ingestions`。接口接收原文并创建持久化任务，返回 202；202 表示已接收，只有任务 READY 才表示已完成入库。查询只展示 Registry 已提交的版本。新版提交前，前一版本继续可查询。

## 两条路径的规则

| 场景 | 使用方式 |
|---|---|
| 生产新增/更新文本、PDF 等文档 | `POST /rag/ingestions`，multipart，显式文档 ID、版本与幂等键 |
| 本地演示或旧客户端迁移期 | `POST /rag/documents` 保留原同步请求和响应契约 |
| 同一生产知识库 | 关闭同步上传，禁止两个版本协议同时写入 |
| 旧图片上传、Obsidian 导入 | 生产旧写开关关闭时一并返回 404；v2 未提供对应批量/图片契约，不应自动改投 v2 |
| 删除、分享 | 网关有独立管理路由；生产 overlay 默认关闭管理写入口。分享可接受控 combined；现有同步删除没有与在途入库事务协调，执行删除前须暂停该文档写入并排空任务 |

`RAG_PRODUCTION=false`、`RAG_LEGACY_WRITE_ENABLED=true` 保留开发兼容。生产显式设置 `RAG_PRODUCTION=true`、`RAG_LEGACY_WRITE_ENABLED=false`。开关约束 `/rag/documents`、`/rag/image`、`/rag/obsidian/import` 的 POST，不隐藏文档读取、查询或分享接口。生产不允许同时启用旧写入口。

## 持久化与发布顺序

1. 备份任务库，使用 `database-migrations` 的 knowledge-ingestion 迁移，执行到 V9。V3 提供恢复字段，V9 增加可空 `PREPARATION_JSON`；历史迁移不修改。应用只校验/使用结构，不执行运行时建表。
2. 配置共享存储，确认 ingest-api、worker 与 query 使用一致的租户分区、向量集合、ES 索引及 Registry。
3. 暂停旧 worker 和旧同步写入，等待在途任务完成或其租约超时，再发布新 worker。迁移期间不混跑旧 worker：旧二进制不识别租约及 MANUAL_REVIEW。
4. 切换网关路由，再启用新入口。既有 docId 必须沿用 Registry 中的 ID；新文档版本从 1 开始，更新必须是已提交版本 + 1。
5. 回滚可以切换路由，但若已有 MANUAL_REVIEW 或租约任务，不得直接启动旧 worker；须先排空或经人工迁移任务状态，保留恢复字段及 V9 准备引用。

| 配置 | 生产要求 |
|---|---|
| `RAG_RUNTIME_ROLE` | combined 或 query / ingest-api / ingest-worker；combined 同样接受生产检查 |
| `RAG_INGESTION_STORE` | ingest-api / worker / combined 使用 `jdbc`，配置 `RAG_INGESTION_DB_*` |
| `RAG_SOURCE_STORE` | ingest-api / worker / combined 使用 `s3`，配置 bucket、endpoint/region 与独立权限 |
| `RAG_REGISTRY_STORE` | `redis`；Redis 持久化、备份与故障恢复由基础设施保证 |
| `RAG_VECTOR_STORE_PROVIDER` | query / worker / combined 使用持久化实现，例如 qdrant |
| `RAG_ES_*` | 混合查询要求 ES 查询开启；生产 worker / combined 启用 ES 时必须 `INDEX_ENABLED=true`、`FAIL_FAST=true` |
| `RAG_GRAPH_ENABLED` | 可开；query 角色开图检索时必须同时 `RAG_GRAPH_REQUIRE_PROVENANCE=true`，让图命中进入版本过滤与文档级判权 |

生产检查验证配置，不会验证 Redis AOF、存储备份或远端数据完整性。ingest-api 不执行 embedding，可保留其内部 in-memory 占位配置；query 不需要入库 JDBC/S3 写凭据。

`deploy/docker-compose.knowledge-production.yml` 可叠加基础 Compose 和 split Compose，提供入口与角色约束、网关拆分路由，并把原 `knowledge-service` 服务名转换为同数据面的只读兼容入口，避免内部客户端继续访问可同步写入的 combined。它不是可直接上线的完整生产部署：split 示例仍含开发账号、MinIO 和 hash embedding 默认值，必须按实际环境替换；公共组件优先复用 dev_infra，不应重复创建。

网关配置：`KNOWLEDGE_INGEST_URI` 指向 ingest-api，`KNOWLEDGE_QUERY_URI` 指向 query，`KNOWLEDGE_ADMIN_URI` 单独承接删除/分享。不设置专用 URI 时全部回退到原 `KNOWLEDGE_URI`，保持未拆分部署兼容。

## 客户端协议

```bash
curl -X POST "$EDGE/rag/ingestions" \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Idempotency-Key: import-orders-guide-v1' \
  -F documentId=orders-guide -F documentVersion=1 \
  -F displayName=orders.md -F category=manual -F file=@orders.md

curl "$EDGE/rag/ingestions/$JOB_ID" -H "Authorization: Bearer $TOKEN"
```

提交需要 `ingest` scope。响应带 `Location: /rag/ingestions/{jobId}`；客户端可轮询该地址。原有字段之外新增 `errorCode`、`failedStage`、`retryable`、`retryCount`、`nextRetryAt`，不返回原始异常。

- 同一租户、幂等键、提交者、文档 ID、版本、内容 SHA-256、文件类型、显示名和分类完全一致，返回原任务，包括已完成任务。traceId 不参与指纹。
- 相同键绑定不同内容或元数据返回 409；并发唯一键冲突后的返回路径也校验指纹。不同幂等键竞争同一文档版本同样冲突。
- 任务查询和重放仅允许原提交者；跨租户或其他用户返回 404。人工重试还要求 `ingest`，已有文档重新检查 edit 权限。
- 网络断开后使用同一幂等键重试，不生成随机新键。跨内容更新必须使用新幂等键和下一版本。
- 对象写入成功而数据库响应不确定时保留原文，避免误删并发获胜任务引用的对象。孤儿对象尚无自动清理器；清理必须核对任务引用并留出提交宽限期，不能对整个 source 前缀设置盲删生命周期。

## 恢复行为

默认最多自动重试 3 次（不含首次执行），间隔从 5 秒开始指数退避，上限 5 分钟。已成功的存储目标不重新执行。KDP-04 在首次写索引前把最终文本块、metadata、向量和文档信息持久化到 S3，并通过任务 revision/租约绑定引用；重试与重启只读取同一快照，不再次解析或调用 embedding。仅从未绑定结果、没有 sink 执行过的新任务允许重做准备。

| 状态/错误 | 行为 |
|---|---|
| PARTIAL / FAILED | 暂时依赖失败，等待 nextRetryAt 后恢复 |
| MANUAL_REVIEW / INVALID_INPUT_OR_PERMISSION | 参数、权限或版本提交错误，需要人工处理 |
| MANUAL_REVIEW / RETRY_EXHAUSTED | 达到自动重试上限，包括反复租约超时 |
| READY | 所有目标处理结束且必要目标成功，Registry 版本已提交 |

修复依赖或配置后，提交者可执行 `POST /rag/ingestions/{jobId}/retry`，返回 202。它恢复原任务并重置自动重试预算，不修改已绑定原文。任务处于运行或成功状态时返回 409；坏文件不能通过同键替换内容，需人工处理该文档版本占用后重新接入，当前没有自动废弃版本接口。

| env | 默认 |
|---|---|
| `RAG_INGESTION_MAX_RETRIES` | 3 |
| `RAG_INGESTION_RETRY_DELAY` | 5s |
| `RAG_INGESTION_MAX_RETRY_DELAY` | 5m |
| `RAG_INGESTION_PROCESSING_TIMEOUT` | 15m（执行租约） |
| `RAG_INGESTION_HEARTBEAT_INTERVAL` | 30s，必须小于租约的一半 |

worker 在解析之前抢占整条任务。心跳与阶段提交共用最新 revision；续期推进 revision，因此 reconciler 的旧快照不能覆盖已经续期的任务。超时旧 worker 在进入下一目标前会停止推进；已经发出的网络写入不能可靠撤销，仍依赖稳定版本主键与幂等存储操作。Registry 使用原子版本条件提交，旧版本不能回退可见性；这不是跨 JDBC、S3、Redis、向量库的分布式事务。

## 观测与验证

### 文档解析预算与错误分类（2026-10-19）

`app.rag.parsing.max-text-chars` / `RAG_PARSING_MAX_TEXT_CHARS` 默认 **2,000,000 字符**，必须大于零；包含解析器输出的空白。超过预算整份解析失败，不把截断正文写入索引。此预算只作用于文件文本提取，不覆盖旧 JSON 直接正文、上传大小、解压体积、页数、OCR、CPU 时间或进程内存。Docker 部署调整值时需向 worker/combined 容器显式传入该环境变量，宿主 `.env` 本身不等于容器环境。

| 任务 errorCode | 处理方式 |
| --- | --- |
| `DOCUMENT_EMPTY` | 无可抽取文本，人工确认是否为空文件或需要 OCR |
| `DOCUMENT_TEXT_LIMIT` | 正文超过预算；在资源评估后调整预算或拆分源文件 |
| `DOCUMENT_ENCRYPTED` | 提供经授权解密后的副本 |
| `DOCUMENT_PARSE_FAILED` | 文件损坏或无法解析，修正输入后重新接入 |
| `DOCUMENT_SOURCE_READ_FAILED` | 原文读取失败，沿用有限退避；耗尽后为 `RETRY_EXHAUSTED` |

前四类进入 `MANUAL_REVIEW`，不自动重试同一坏文件。该分类复用已有任务 `errorCode` 字段，不新增数据库迁移；原始异常只在服务端日志中记录。旧同步 `/rag/documents` 对输入错误仍返回 400，暂时读取故障返回 503，保留 `X-Error` 并附加稳定的 `X-Error-Code`；响应不包含底层异常或原文件名。

Markdown、父子及语义嵌套切分的最终 `index` 改为文档版本内唯一。Markdown 使用 CommonMark 0.25.1 识别顶层 ATX/Setext 标题，代码围栏、缩进代码和 HTML 内伪标题不形成章节；混合 H1/H2 正确重置路径。非标题正文不再把首行伪装为 `section`，原文首行代码缩进和行末空白保留。

发布这些切分规则前，应排空或隔离旧规则产生的在途/部分成功任务；旧任务应由原处理版本完成或经人工核对后恢复，避免跨规则重试混用向量/ES 分块。历史被覆盖的块须以新文档版本重新入库；本次代码发布不自动重建索引。持久化派生结果与文件解析阶段硬截止已经实现；模型/存储阶段预算与租户公平性继续由 KDP-05-B 完成，详见[生产优化方案](知识库文档解析生产优化.md)。

- `knowledge.ingestion.jobs{status}`：任务库各状态数量。
- `knowledge.ingestion.oldest.pending.seconds`：最老未完成任务的年龄。
- `knowledge.ingestion.failures{stage}`：worker 各阶段失败次数，可结合处理量计算失败率。
- `knowledge.ingestion.stage.duration{stage,outcome}`：阶段耗时及成功/失败次数，可计算失败率。
- `knowledge.ingestion.commit.latency`：从接收到 READY 的总延迟。

计数/耗时指标由当前进程记录，状态与积压从任务库读取；指标不带租户或 jobId 标签。排障用 traceId 与服务日志。若启用通用 async-task 镜像，细粒度阶段与人工恢复状态仍以 `/rag/ingestions/{jobId}` 为准。

仓库验证：`mvn -o -pl knowledge-service,edge-gateway -am test`。覆盖幂等冲突、跨用户隔离、版本条件提交、租约续期与旧 worker 停止、退避上限、JDBC 恢复字段及网关路由。真实 MySQL/S3/Redis/向量库的断电恢复和吞吐压测需要在目标环境另行执行。


### 不可变准备结果（KDP-04）

- 默认对象路径为 `documents/prepared/<tenant>/<job>/v<version>/<sha256>/source`，复用原文 bucket，但使用独立前缀。内容与任务身份、原文指纹、schema 和处理版本绑定；校验大小、SHA-256、块/向量数量及维度。
- `RAG_INGESTION_PREPARED_MAX_BYTES` 默认 67,108,864（64 MiB），读写均受限；`RAG_INGESTION_PROCESSING_VERSION` 默认 `knowledge-structured-v2`，生成行为变化时提升版本。旧快照不因当前配置/模型变化而重新生成。
- 缺失或临时 I/O：`PREPARED_RESULT_UNAVAILABLE` 有限退避；损坏/错配：`PREPARED_RESULT_INVALID`；超限：`PREPARED_RESULT_LIMIT`；不支持 schema：`PREPARED_RESULT_VERSION`；不安全旧任务：`LEGACY_PREPARATION_REQUIRED`。后四类进入人工处置，不悄悄重算。
- 迁移到 V9 后先停止旧 worker，再启动新 worker。没有准备标记的旧任务仅在 RECEIVED 且所有 sink PENDING 时自动接管；旧 PROCESSING/PARTIAL 即使被 reconciler 重置也不能证明没有副作用。不得把旧任务手动伪装成新 PENDING 来绕过检查。
- worker 需对原文与快照 `GetObject`，仅对 `documents/prepared/*` 增加 `PutObject`。split Compose 策略已同步；ingest-api 对快照前缀显式禁止 Put/Delete。自定义原文 prefix 时同步调整对应策略。已有对象不自动删除，未知绑定结果不能触发清理；保留期沿用原文/任务治理，孤儿清理须核对引用及提交宽限期。
- 回滚先停止消费并保留已绑定新任务，不能交给不理解快照的旧 worker；数据库扩展列不回删。实际迁移、IAM 策略发布、历史任务处置与重建索引需按目标环境发布流程执行，本次仅交付代码与验证。
- `python3 deploy/test-ingestion-prepared.py` 在 dev_infra 的随机 MySQL schema 与 S3 测试对象验证重建 worker 的恢复；使用已有本机私有凭据，只清理本测试资源。没有执行真实计费模型、线上迁移或断电灾备。


### 独立解析进程（KDP-05-A）

应用缺省 `RAG_PARSING_EXECUTION_MODE=forked`，生产 worker/combined 配置禁止 in-process。每次文档解析独立 JVM、每进程不启动 Spring 或继承服务凭据。下表为保护缺省值，按实际语料/硬件调参，不代表 SLA。

| 环境变量（前缀 `RAG_PARSING_`） | 默认值 | 含义 |
| --- | --- | --- |
| `MAX_INPUT_BYTES` | 52428800 | 输入暂存 50 MiB |
| `MAX_TEXT_CHARS` / `MAX_RESULT_BYTES` | 2000000 / 16777216 | 正文字符/结果字节上限 |
| `MAX_PAGES` | 500 | PDF 页数上限 |
| `MAX_TEMPORARY_BYTES` / `MAX_TEMPORARY_FILES` | 134217728 / 1000 | 单任务目录监测预算 |
| `MAX_PROCESSES` / `HEAP_MIB` | 2 / 256 | 服务实例并发解析数/子 JVM 堆 |
| `TIMEOUT` / `INPUT_TIMEOUT` / `TERMINATION_TIMEOUT` | 120s / 60s / 5s | 解析截止/读边界暂存检查/强制退出确认 |

`app.rag.parsing.temp-root` 默认系统临时目录下的 `knowledge-parser`。S3 的 `RAG_SOURCE_CONNECT_TIMEOUT`、`RAG_SOURCE_READ_TIMEOUT`、`RAG_SOURCE_CALL_TIMEOUT` 默认 2s、30s、2m；单次阻塞读取靠源 SDK 的超时，不声称任何 InputStream 都能强杀。split worker 的容器默认 3g 内存、2 CPU、256 pids、512m `/tmp` tmpfs；其他部署须提供等价限制。目录监测可能短暂超调，Xmx 不等于总 RSS，fork 不隔离同用户文件/网络访问。

新增错误：`DOCUMENT_INPUT_LIMIT`、`DOCUMENT_PAGE_LIMIT`、`DOCUMENT_RESOURCE_LIMIT`、`DOCUMENT_PARSE_TIMEOUT` 进入人工处置；`DOCUMENT_PARSER_PROCESS_FAILED`、`DOCUMENT_PARSER_TERMINATION_FAILED` 同样不自动反复重试崩溃输入，但同步接口返回 503。`DOCUMENT_PARSER_UNAVAILABLE`、`DOCUMENT_PARSER_BUSY` 与原文读取错误有限退避，并返回 503。其他输入错误保持 400。无法确认进程退出时保留目录/并发额度并通知运维，不能继续放大失控任务。

OCR 与递归附件默认禁用；选择性 OCR 的显式开启方式和边界见后面的 KDP-06-C。旧目录 SPI 不自动得到这里的隔离保证。完整限制及真实 Linux 验证见 [KDP-05-A](../delivery/knowledge-parsing-hardening/KDP-05-A.md)。


### 结构切分、来源与兼容（KDP-06-B）

multipart 文件与异步任务使用 `ParsedDocument` schema 1；二进制按内容识别，纯文本 CSV/Markdown 用后缀消歧。CSV/Excel 的每组行携带表头、逻辑行号/列组/工作表；Markdown/Word 章节与 PDF 页码进入 metadata。首非空行默认表头，公式读缓存、无文本页、未支持辅助结构会产生 `parsing_warnings`；这些告警不意味着 OCR 或复杂版面已正确识别。

`RAG_PARSING_MAX_STRUCTURE_UNITS` 默认 100000（块/行/单元格合计），`RAG_CHUNKING_MAX_CHUNKS` 默认 20000；超限返回 `DOCUMENT_STRUCTURE_LIMIT`，人工检查输入/预算，不静默丢内容。长表先按行/列切，单个长值分段标 `source_row_fragment`，长代码标 `source_code_fragment` 并保留缩进。单个无法容纳的表头明确失败。原有字符/token 预算作用于最终结构块；增强模型整体预算继续由 KDP-05-B/06-D 完善。

`KnowledgeHit.sourceMetadata` 为可选加法字段，默认空集合；含 `source_page/sheet/row_start/row_end/columns/line_start/line_end/paragraph/location` 等来源及章节/质量告警，身份仍使用原 tenant/doc/version/visibility 字段。Contextual 模型前缀单独存 `context_prefix`，引用/检索 API 正文使用 `source_text` 原文，避免生成内容伪装证据。

ES 新字段 `sourceMetadata` 是 `object, enabled=false`，仅 `_source` 回读，不做动态字段索引。建议发布身份预建映射，worker 已预建时只检查；缺失时自动加法扩展需要 mapping 管理权限；类型不兼容明确失败。历史文档没有该字段仍可查，不自动回填或重建。该结构切分阶段的处理版本为 `knowledge-structured-v2`；KDP-06-C 起缺省为 `knowledge-structured-v3`，已绑定旧版本准备结果继续直接恢复。详见 [KDP-06-B](../delivery/knowledge-parsing-hardening/KDP-06-B.md)。

### 流式输入与批次预算（KDP-05-B1）

`/rag/ingestions` 以流读取 multipart，计算完整 SHA-256 并暂存私有文件后发送 S3；不再调用 `getBytes()`。超限返回 `INGESTION_INPUT_LIMIT`（413），实际大小不符为 `INGESTION_INPUT_SIZE`（400），实例暂存饱和为 `INGESTION_UPLOAD_BUSY`（429）。响应和幂等键/提交者/版本规则不变，失败清理本地暂存，数据库结果未知时保留来源对象。

模型按块数、估算 token、UTF-8 字节同时分批，拒绝整文预算超限或无效模型响应；sink 从绑定快照分批 upsert，重试主键不随批次大小变化，REGISTRY 仍最后提交。图谱可靠任务等待实际写完，每批检查租约，失租停止后续调用。默认值、配置与边界见 [KDP-05-B](../delivery/knowledge-parsing-hardening/KDP-05-B.md)。本阶段完成后仍需 B2 跨副本公平调度。

### 公平领取与有界执行（KDP-05-B2）

先由 migrator 应用 `knowledge-ingestion/V10__ingestion_fair_admission.sql`，应用账号仍只需既有 schema 的 SELECT/INSERT/UPDATE/DELETE。worker 启动检查守卫表；默认每实例 `RAG_INGESTION_WORKER_CONCURRENCY=2`，跨实例 `RAG_INGESTION_GLOBAL_CONCURRENCY=4`、每租户 `RAG_INGESTION_TENANT_CONCURRENCY=1`。`memory` store 仅能控制同进程共享对象，生产多副本必须使用同一个 JDBC 任务库。

额度和领取轮次在一个短事务内完成。守卫表首次领取时绑定全局/租户额度，不同配置的副本拒绝领取并报告 `INGESTION_ADMISSION_CONFIG`；不会以较大值覆盖当前策略。运维调额须停止所有领取者、检查在途租约后同时调整各副本配置与守卫行的 GLOBAL_LIMIT/TENANT_LIMIT，再重启；保留 GRANT_SEQUENCE 与租户轮次。启用或回滚不能混跑旧 worker 并宣称公平额度有效；迁移不会自动更新正在运行的业务进程，本次也未执行生产迁移。

持久数据库是等待队列，独立线程池使用零等待队列，实际运行后才领取，拒绝不会丢任务。`RAG_INGESTION_WORKER_SHUTDOWN_TIMEOUT=30s` 有界等候后中断；未完成工作从持久租约恢复。`RAG_INGESTION_EXECUTION_TIMEOUT=30m` 在批次边界检查，心跳不能无限延长该预算。必须保持 worker 时钟同步；正在发送的网络请求可能在失租/关闭后继续完成，不能将逻辑额度宣称为任意网络分区下的绝对物理请求上限。

监控 `knowledge.ingestion.executor.active/available/rejected/duration`、`knowledge.ingestion.queue.wait` 及既有任务状态/最老积压/阶段延迟指标。没有租户 ID 高基数标签。TTL 显式包装桥接 TenantContext/MDC，并捕获/恢复当前 OTel context；持久 job 只保留原有 traceId 关联，不虚构跨进程父 span。数据库事务不跨线程。

上述 500000 token 仍是单阶段 embedding 输入限额；KDP-06-D 另有跨阶段总预算，不能与真实账单混淆。Graph 当前是规则抽取，无 Graph LLM 调用。

JDBC 还分别提供 `RAG_INGESTION_DB_CONNECTION_TIMEOUT=3s`（池等待）、`DB_VALIDATION_TIMEOUT=1s`、`DB_CONNECT_TIMEOUT=2s`、`DB_SOCKET_TIMEOUT=10s` 与 `DB_QUERY_TIMEOUT=5s`（后四项均有完整 `RAG_INGESTION_` 前缀）。MySQL 驱动参数通过数据源传入，若 JDBC URL 自行覆盖同名参数需保持一致；0 不能用于关闭上限。SQL 与领取短事务共享 query-timeout。新增握手不响应测试证明默认机制能结束等待，不能用它代表任意数据库/网络故障下的恢复时间。


### 选择性 PDF OCR（KDP-06-C）

`RAG_PARSING_OCR_ENABLED` 缺省 `false`。split worker 构建 `knowledge-service/Dockerfile` 的 `ocr` target，含 Tesseract、`chi_sim`、`eng`、`osd`；运行期开启后仅结构文件入口的 PDF 候选页执行本地识别。查询/兼容基础镜像的 `runtime` target 不含引擎；combined 若要开启，须显式采用 OCR target 和上述环境变量。宿主环境变量不会自动传给容器；其余调参通过 Compose override 的 worker `environment` 显式传入。

| 参数（`RAG_PARSING_OCR_` 前缀） | 缺省与含义 |
| --- | --- |
| `LANGUAGES` / `DPI` | `chi_sim+eng` / 200；本地语言包与渲染分辨率 |
| `MAX_PAGES` / `MAX_PAGE_PIXELS` / `MAX_TOTAL_PIXELS` | 50 / 12000000 / 120000000；整文候选页及渲染工作量预检查，超限不处理半份 |
| `MIN_NATIVE_CHARS` / `IMAGE_COVERAGE` | 40 / 0.35；无文本有绘制内容页、少字含图页或大图页触发；面积是保守估算，不是版面准确率 |
| `MIN_CONFIDENCE` | 55，字符加权引擎置信值，**不是实测准确率** |
| `MAX_OUTPUT_BYTES` | 2097152，单页 TSV 输出预算；父进程另有临时目录/结果总预算 |
| `PAGE_TIMEOUT` / `TOTAL_TIMEOUT` | 20s / 90s；与解析总时限 120s 共同生效，不相互延长 |

保留原生文字；OCR 只抵消同次数的原生整行重复，不随意删除子串/重复表值。追加层不保证阅读顺序，有明确告警。每页记录 `source_extraction_method`、`source_native_chars`、`source_ocr_chars`、`source_ocr_confidence`，并沿快照/检索来源白名单传递。PDF 本身旋转字段仍表示文件声明，不伪造引擎校正角度。仅全白栅格按空白标识，低对比/噪声不能静默丢弃。

`DOCUMENT_OCR_LIMIT/TIMEOUT/QUALITY` 使整份失败并进入人工处置；`DOCUMENT_OCR_UNAVAILABLE/FAILED` 返回服务故障，修正引擎/语言/环境后人工重试，不陷入自动重试循环。进程环境不带服务凭据；先请求 JVM 有界退出以清理 native 子进程，再强制终止可见后代。fork 仍非恶意文件安全沙箱，宿主 OOM/SIGKILL 的竞态不等于完整进程容器隔离。

处理版本升为 `knowledge-structured-v3`；OCR 关键配置进入准备 profile，具体页策略进入来源 metadata。旧快照只回读，不因开关变化重新 OCR。不改变业务版本可见性，不自动回填旧索引。引擎/语言包版本和合成验收见 [KDP-06-C](../delivery/knowledge-parsing-hardening/KDP-06-C.md)，可复现入口 `python3 deploy/test-parsing-ocr.py`（先按 TEST_RESULT 构建 jar 和测试 classpath）。


### 模型工作量与上下文成本（KDP-06-D）

一次准备共享 `app.rag.ingestion.resources` 的以下预算；同步文件/JSON 和可靠 worker 都生效。超限返回 `INGESTION_MODEL_WORK_LIMIT` 或 `INGESTION_METADATA_LIMIT`，不会截断写入或自动重试。

平台 embedding 的文档任务前缀计入输入 token/字节预算，引用原文不受影响。同步入口的 `dimension()` 按一次逻辑操作保守占用额度，防止默认 `embed("test")` 探测漏计；固定维度返回同样占用该额度。覆盖旧版复用已校验 store。启动初始化、独立删除及自定义 SDK 内部调用不在这次准备的精确 HTTP 统计范围内。

| 环境变量 | 缺省 |
| --- | --- |
| `RAG_INGESTION_MAX_MODEL_INPUT_TOKENS` | 1000000，语义窗口 + 完整上下文 prompt（含 framing 余量）+ 最终 embedding 的估算输入 |
| `RAG_INGESTION_MAX_MODEL_CALLS` | 512 次逻辑请求，失败请求也计入 |
| `RAG_INGESTION_MAX_CONTEXTUAL_CALLS` | 128 次；已知整批提示预检查，超额时不先调用部分块 |
| `RAG_INGESTION_MAX_CONTEXT_PROMPT_TOKENS` | 8192，单个完整提示 |
| `RAG_INGESTION_MAX_CONTEXT_PREFIX_TOKENS` | 256，请求输出参数及返回结果校验；超长前缀弃用并标记，保留原文 |
| `RAG_INGESTION_MAX_METADATA_BYTES` | 16777216，所有块 metadata JSON 总字节，包含重复父块和原文 |

Contextual 缺省关闭；开启时窗口以当前章节/邻近原文为中心，`max-doc-chars` 限制窗口大小。`source_text` 继续存原文，生成前缀只用于检索。新增 `chunking_actual_strategy` / `contextual_status` 可随来源返回，用于区分真正的语义路径、结构切分、递归降级和前缀弃用。

`RAG_CHUNKING_SEMANTIC_INTERPOLATE_PERCENTILE` 缺省 `false`；开启才使用线性分位候选。短文确定性夹具通过不意味着生产 Recall 更高，因此没有自动改变全局策略。新处理版本为 `knowledge-structured-v4`；历史已绑定快照原样恢复，配置变化不会重算。

这些是按 tokenizer 的资源预算，不是提供方准确用量或金额；平台已有网关租户预算/审计继续使用。split worker 的 `RAG_EMBEDDING_MAX_RETRIES` 和 `GATEWAY_MAX_RETRIES` 为 0，统一由 job 控制重试；combined 和自定义 provider 的透明重试需另计。自定义 `ContextualEnricher` SPI 兼容保留，但其内部额外模型调用须主动使用预算接口，不能自动宣称受内置治理。不会强制终止一个已发出的模型 HTTP 请求，仍依赖 SDK 超时。度量与对照见 [KDP-06-D](../delivery/knowledge-parsing-hardening/KDP-06-D.md)。
