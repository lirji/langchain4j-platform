# 可用于简历的实测表述

## 推荐版本

**企业级 RAG：**支持多格式文档解析与多策略分块，将内容写入 Qdrant 和 Elasticsearch；
基于可插拔 RetrievalSource 实现向量、BM25、关键词和知识图谱四路召回及 RRF 融合。
在 200 条基于项目文档生成并做来源校验的评测集上，Recall@10 从 80.0% 提升至 98.5%，
MRR 从 0.534 提升至 0.880；50 条回答的引用 ID 有效率为 89.7%。

**多 Agent 编排：**实现基于 Kahn 拓扑分层的 DAG 引擎，支持环检测、同层并行、
Synthesis 汇总及 Critic/Replanner 质量闭环；在 6 节点冷请求对照中，并行拓扑平均耗时
由 61.7 秒降至 39.4 秒，下降 36.1%（每组 5 次）。

**NL2SQL / ChatBI：**实现自然语言生成 SQL、只读执行和结果解读，并通过 SELECT 校验、
表白名单、强制 LIMIT、执行超时和租户条件构建安全护栏；在基于固定种子库构造的
150 条业务问数集上，最终 SQL 执行成功率 99.3%，结果正确率 95.3%。

**语义缓存：**实现租户隔离的 Redis L1 语义缓存；在 30 组完全相同问题的受控重复测试中，
命中后平均响应时间 6.7 ms、P95 10 ms，较冷链路平均 2.46 秒降低 99.7%。

## 面试追问速答

### 这 200 条 RAG 数据怎么来的？

从仓库 20 份项目文档中每份生成 10 个问题，保留源文件和参考答案，并机械校验源文件存在、
ID 唯一和标注文档名一致。它是项目文档合成集，不是生产用户问题，也不冒充全量人工标注集。

### Recall@10 怎么算？

每题标注一个相关文件。该文件任意 chunk 出现在 Top-10 就记 1，否则记 0，最后对 200 题取平均。
因此本数据集上的 Recall@10 与 Hit@10 相同。

### 80.0% 的基线是什么？

相同文档、分块、embedding 和 Top-K 下只开启 Qdrant 向量召回；98.5% 组开启向量、内存关键词、
Elasticsearch BM25、Graph 四路召回并用 RRF 融合。两组都关闭 query expansion 和 reranker。

### Agent 耗时怎么测？

同一类 6 节点任务分别构造成完全线性依赖和两层并行 DAG，关闭 Replanner，并给每次请求加入
唯一评测标识规避 LiteLLM 精确缓存。两组各跑 5 次，比较经 edge 的端到端墙钟时间。

### Agent 任务完成率由谁判断？

20 题在运行前固定必需词和禁用词，由脚本做确定性检查，不采用模型自己的 Critic 分数作为最终
完成率。本轮 Replanner 关闭为 70%，开启为 75%，但开启组 P95 升到 140.3 秒并出现一次 500，
所以没有把该小幅提升写进简历亮点。

### NL2SQL 为什么写“最终”而不是“首次”？

当前接口只暴露最终 SQL 和结果，没有 attempt 级明细。`HTTP 2xx && sql != null` 只能证明经过
可能的自修复后最终成功，不能证明第一次生成的 SQL 就成功。

### 95.3% 怎么判断？

150 条问题基于固定 MySQL 种子库构造。脚本把返回 rows 做数值和结构标准化后与预先写定的黄金值
比较；SQL 文本不同但结果等价也算正确。

### 引用准确率 89.7% 是什么含义？

它是引用 ID 有效率：回答中的 39 个 `[doc=...]` 标记有 35 个可在同问题 Top-10 检索结果中找到。
它不等于引用片段完全支持答案；要证明后者还需要片段级蕴含评测。

### 为什么没有“支持租户数量”？

已注册租户数不等于系统容量。本轮没有按目标活跃租户比例、QPS、P95、错误率和跨租户隔离做容量
压测，因此没有填写无法证明的数量。
