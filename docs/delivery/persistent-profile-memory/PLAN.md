# 长期画像持久化：M1-PERSIST

## 范围与决策

用户要求将长期记忆的内存存储改为持久化存储。本切片替换用户画像存储，不实施知识运营、记忆审批、抽取策略改造或 Java 版本升级。HTTP DTO、召回顺序、文本去重与容量淘汰兼容现有行为。

- 权威存储为现有 MySQL 8.4 的独立 conversation schema，复用 JDBC/Hikari/Flyway；不新增中间件或升级版本。
- 默认画像 store=jdbc；显式 in-memory 仅保留给开发及现有单元测试，不作为数据库故障回退。
- 使用画像所有者行锁串行化同一 tenant/user 的去重、写入、淘汰和清空。不同所有者独立执行。
- 所有者键由长度定界的 tenant/user SHA-256 产生，避免分隔符歧义和数据库默认大小写不敏感导致跨身份混桶。
- 原子事务只包数据库操作，不持锁调用模型。条目按数据库插入序号排序；客户端时间不作为淘汰顺序。
- 迁移进程持 DDL 权限，应用仅 DML，启动验证表存在。连接池有界、配置校验，失败不伪装成空画像。
- 去重及容量逻辑以已有实现/测试为契约，移出对内存类的依赖；正式持久化字段使用语言中立类型。

## 技术未知与影响

现有 conversation 无 JDBC 数据源，采用 channel-service 已有的条件数据源装配方式，避免功能关闭时自动建库连接。新增 schema 需同步 Compose、Helm、dev_infra 生成器和现有静态迁移门禁。所有新依赖复用现有 BOM；MySQL 驱动遵循现有服务依赖管理。

## 实施与验收

1. 补存储契约测试（恢复、去重、隔离、清空、淘汰、并发）和装配测试。
2. 增加持久化实现、版本化迁移和默认配置。
3. 同步运行拓扑与使用说明，测试真实 MySQL 迁移、重建连接池、多实例竞争和事务失败回滚。
4. 执行相关 Maven 回归、配置门禁、Code Hygiene 和差异检查；仅提交本任务文件。

## 回退与限制

旧内存数据没有既有导出/持久化渠道，不宣称自动迁移旧 JVM 堆中的数据。若需保留正在运行实例的画像，应在停机前另行设计授权导出。
停用画像功能可回退入口；保留新增 schema，不执行 down migration。回退到旧二进制/显式内存模式不会读取数据库画像，必须明确数据可见性差异。
本切片保证存储操作的事务一致性；清空之前已经发起、清空之后才完成的模型抽取仍可能提交新记忆，此项属于后续治理切片的 generation fencing，不宣称已解决。
本轮不运行真实付费模型，不部署生产。现有 Java 安全扫描债务保持原结论，不降低门禁。
