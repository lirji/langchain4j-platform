# KDP-05-B：输入、模型批次与公平执行

接续 `1b5b3b7`，用户已要求按顺序持续实施。当前设计/实现中，不代表验收已完成。

## B1：流式接入与批次预算

- multipart 不调用 getBytes：按输入上限流式暂存私有文件，同时 SHA-256；获得完整哈希后沿用现有 content-addressed 对象键、所有者/幂等校验和任务创建顺序。S3 从可重开文件发送，避免 SDK 重试依赖一次性流；旧 byte[] 编程接口保持兼容。
- 输入并发与临时文件有界、异常/重放均清理自有临时文件；来源对象在数据库结果未知时仍不得删除。Servlet 接收阶段与单次阻塞流不冒充可强杀操作。
- embedding 按条数、估算 token、UTF-8 字节分批，单块/整文/向量预算明确；验证返回数量、维度、有限浮点。不会通过静默截断或丢块满足预算，不新增嵌套重试。
- VECTOR/ES/GRAPH 按批写，稳定 ID 仍由文档版本与最终 index 决定；整 sink 失败后复用已绑定快照重放，部分批次可重复 upsert，REGISTRY 最后提交可见性。
- 准备结果最终仍是有界快照，不虚称全链路常量内存；未绑定前 embedding 失败重试可能重复计费调用，但受任务重试/整文预算约束。

## B2：有界执行与跨副本公平

- 复用任务库作为分布式准入权威，以事务/条件更新保护全局和租户在途额度；仅本地 Semaphore 不足以约束多个 worker 副本。领取/续期/释放与现有租约、revision 和恢复规则一致，失租后每批停止推进。
- 显式独立有界线程池，队列饱和不消费/不丢持久化任务；延续已有轮询维护机制，不在此局部优化中新增外部调度中间件。租户顺序应防止单热点租户堵住候选前列。
- 任务身份/trace 从持久化 job 恢复，线程池入口与退出正确清理，复用已有 TTL/追踪设施；不传事务资源。停机停止接收、有界等待，剩余持久化任务由租约恢复，不宣称撤销已经发出的网络请求。
- CPU/堆/并发/连接预算以保守缺省和配置说明交付，不能从合成小样本推导生产 SLA。

## 必要验证

流式输入/哈希一致性、无 getBytes、大输入/中断/IO 失败清理、幂等/跨用户/版本守卫；批次边界、长块/整文预算、429/中途失败后稳定重放；真实 MySQL 多领取者/跨副本额度与租户公平、混合大/小文档、停机/失租/重启和上下文不串。延续 KDP-04 不可变结果与现有格式语料回归。

## B1 当前实现与边界

已实现流式上传、SHA-256、可重开文件 S3 上传、实例/租户暂存准入；embedding 三重批次预算与输出校验；VECTOR/ES/GRAPH 分批、每批权威租约检查、可靠图谱同步确认。同步兼容接口也应用批次预算，先完成预算检查再删除旧版本，但仍不提供可靠任务的版本原子可见性。B2 尚未实现，不能将实例上传额度称为跨副本公平。

默认保护值：输入 50 MiB、实例暂存 4/租户 1、读取预算 60s；模型批次 32 块/8192 估算 token/1 MiB，单块 2048 token，整文 500000 token/16 MiB，向量 32 MiB，准备阶段 10m。`RAG_INGESTION_*` 与 YAML 配置对应；tokenizer 默认 gpt-4o-mini，仅是本地估计，其他提供方应按实测调整。字节批次是文本/metadata/float 逻辑载荷，不是线协议大小。

准备预算和上传读取预算在调用边界检查，不会中止已发出的阻塞 I/O；提供方/对象客户端仍须配置超时。不可变快照仍有整文受限驻留；未绑定前的失败可再次调用模型，整 sink 重放可能再次写已完成批次。split worker 的 embedding SDK 重试设为 0，由 durable job 统一负责重试；combined 兼容路径仍服从原客户端配置。

Servlet multipart 落盘在应用暂存准入之前，应用额度不能替代入口请求/上传并发控制。Compose combined /tmp 为 768 MiB，ingest-api 与 worker 各 512 MiB，作为容器硬上限；调整副本/上传限制应一起核算。进程被强杀可能遗留临时文件，容器临时盘生命周期与运维清理需纳入容量监控，正常失败/关闭路径只清理自有文件。

本地证据：流式 15 项、首轮批次 29 项通过；补充重放 19 项中 1 项真实 S3 条件跳过，其余通过；随机 MySQL/S3 6 项均通过，含 5 MiB 流式往返哈希/跨租户拒绝。四种 CI Compose 组合与 runtime hardening gate 通过。完整模块回归修正同步维度守卫后 684 项、0 失败/错误、10 跳过，B1 验收通过；命令和指纹见 TEST_RESULT。

## B2 实施决定

跨副本准入使用一个短事务守卫行，原子完成全局/租户有效租约计数、按租户最近领取序号选择任务、revision CAS 领取及公平序号推进。模型/对象/索引调用不在事务内。每租户最近领取序号持久化，重启不恢复成固定热点顺序；已租出的任务不进入候选。增加领取/活跃计数索引，真实 MySQL 竞争验证后再确认性能边界。

缺省本地 2 个执行线程、数据库全局 4 个/租户 1 个在途任务，数据库持久队列不预取到无界内存队列。额度策略首次领取绑定到守卫行，副本配置不一致拒绝领取；调整需停止领取并协调所有副本及守卫配置，不自动采用最大值。迁移只新增表/索引，旧 worker 不受新准入约束，因此启用时须停止旧 worker，不能混跑并宣称额度有效。

线程池用零等待队列与明确拒绝恢复，线程获取本地槽位后才领取数据库任务；饱和时任务留在数据库。业务上下文按用户规范使用 TTL 2.14.5 的显式 Runnable 包装，桥接已有 TenantContext/MDC，任务身份仍从 job 重建；不启用 Java agent、不传播数据库事务。版本/API/Java 21 修正依据 [官方 release](https://github.com/alibaba/transmittable-thread-local/releases/tag/v2.14.5) 与 [TtlRunnable 文档](https://alibaba.github.io/transmittable-thread-local/apidocs/2.14.5/com/alibaba/ttl/TtlRunnable.html)。

租约是逻辑执行权边界；暂停/网络分区后已发出的请求不能撤销，旧请求可能与恢复任务短暂重叠，靠版本稳定 ID 与快照保证重放。全局额度不冒充任意网络分区下的物理请求绝对上限。停机停止领取、等待有界时间、再中断等待，尚未完成的持久任务通过租约恢复。
