# KDP-04：持久化准备结果与重试一致性

2026-10-19，基线 `a63a167`；用户已授权按优先级实施。范围为同一入库任务的最终文本块、metadata、向量及文档信息在重试/重启后保持一致。状态与验收结果只在 [PROGRESS_STATE](PROGRESS_STATE.md) 维护。

## 当前问题与不变量

Worker 每次重新 prepare，却跳过已成功的 sink；当配置、增强模型或降级分支改变时，VECTOR 与 ES 可得到不同内容。本项要求：任何 sink 首次执行前，最终准备结果必须已持久化并绑定任务；所有后续执行读取同一结果。准备阶段尚未产生 sink 副作用时允许重新准备，但不能替换已经绑定的结果。

## 实施契约

1. 复用现有 S3 客户端、bucket；worker 原文只读权限之外增加准备结果前缀的 PutObject，ingest-api 对该前缀禁止 Put/Delete，使用原文 prefix 下独立的 `prepared` 子前缀；对象路径包含租户、任务 ID、版本和内容 SHA-256。内存实现仅用于现有 dev/test 模式。没有新增中间件。
2. 保存版本化 JSON 数据模型，不直接序列化 LangChain4j 对象：任务/租户/文档/原文指纹、处理版本、配置描述、DocumentInfo、块文本与 metadata、最终 float 向量。向量和文本一同固定，重试不再次调用模型。对象大小和校验和必须匹配，向量必须有限、同维度且与块数量对应。
3. `KNOWLEDGE_INGESTION_JOB` 增加可空 `PREPARATION_JSON`，由 V9 扩展迁移提供并带字段注释。它只保存协议版本、处理版本和对象引用，不保存大正文。旧数据为 NULL，新提交任务显式保存“尚未准备”标记，解决旧任务是否曾产生副作用无法判断的问题。
4. 顺序：准备 → 写结果对象 → 读回验证 → 在最新租约/revision 下 CAS 绑定引用 → 执行 sink。任何绑定冲突立即停止，旧 worker 的对象不能替换新引用。写对象后崩溃而未绑定仅产生未引用对象，不产生索引副作用；未知提交结果不得删对象。
5. 已绑定结果缺失、校验失败或格式版本不支持时，返回稳定错误码，不回退重新解析。临时对象存储 I/O 沿用有限退避；损坏、超限、旧不安全任务等进入人工处置。错误响应不暴露正文、对象位置或底层异常。
6. 新任务通过明确准备标记区分“安全地重做 prepare”与“必须复用结果”。旧 RECEIVED 且所有 sink 均 PENDING 的任务可由新 worker 初始化；其他没有标记/引用的旧任务默认人工处置，尤其不能把 reconciler 重置成 PENDING 当作从未写入的证据。
7. 向量写入以快照的实际向量维度调用已有 collection 维度守卫；若目标集合不兼容仍失败，不重新嵌入或重建集合。模型切换及历史索引重建不在本项执行范围。

## 配置与兼容

- 结果对象预算缺省 64 MiB，可通过 `app.rag.ingestion.prepared.max-bytes` 调整；序列化及读取均有界，超限整项失败。该预算不替代后续 KDP-05 的进程隔离。
- `app.rag.ingestion.prepared.processing-version` 标识生成流程，缺省 `knowledge-prepared-v1`；发布解析/切分/增强/模型行为变更时应更新它。快照同时记录非敏感的切分配置与模型描述；配置变化不会使已绑定结果失效或触发重算。
- 先执行 V9，再停旧 worker、处置旧在途任务、启动新 worker。新旧 API 可在扩展列上共存；**旧 worker 不得与新 worker 混跑，也不得接手已采用快照的新任务**。回滚执行器须先停消费并保留新任务/对象，不能直接用旧二进制重试它们。
- 快照与原文同为受控私有数据。沿用现有逻辑删除和任务保留边界，不新增自动物理清理；只有核对全部引用、权限及提交宽限期后才可清理孤儿对象。文档墓碑仍阻止旧版本提交重新可见；保留期和受控物理清理另按既有数据治理要求执行。

## 验收

- 先复现 VECTOR 成功、ES 失败后再次准备产生不同文本的错误。
- 重启 worker/重建 JDBC store 与 S3 adapter、改变准备器后仍使用第一次结果；解析和模型调用次数不增加。
- 租户/任务/版本/原文指纹错配、对象截断/缺失、错误 schema、预算超限，不写任何 sink 且不静默重算。
- 并发租约争用、写对象后失租、CAS 响应丢失、重复重试及旧任务恢复；已有引用不被替换。
- 内存/H2 聚焦测试后，在共享 dev_infra 的随机隔离 MySQL schema 与独立 S3 测试前缀补验实际持久化。只操作本次测试资源，不迁移业务库、不部署应用、不调用计费模型。
